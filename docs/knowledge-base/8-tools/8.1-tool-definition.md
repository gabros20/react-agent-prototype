## Overview

Tools extend LLM capabilities beyond text generation—they enable agents to fetch data, modify state, and interact with external systems. But tool quality directly impacts agent reliability. Vague descriptions cause wrong tool selection. Missing validation causes schema mismatches. Inconsistent naming causes confusion.

Tool design requires as much attention as prompt engineering. Per Anthropic (2024): "Invest just as much effort in creating good agent-computer interfaces as you would for human-computer interfaces."

**Key Research Findings** (2024-2025):

-   **90%+ tool selection accuracy** achievable with clear descriptions and namespacing
-   **<0.5% invalid tool calls** with strict schema validation
-   **70% latency reduction** with parallel tool execution enabled by proper I/O classification

**Date Verified**: 2026-01-03

## The Problem: Tools That Confuse LLMs

### The Classic Challenge

An agent has 15 tools available. The user asks to "update the page title." The agent calls `search_content` instead of `update_page` because both descriptions mention "page" and "content" without clear differentiation.

```
Tools available:
- search_content: "Search content by query"
- update_page: "Update page content"
- get_page: "Get page"

User: "Change the title of the about page to 'About Us'"

Agent thinks: Both update_page and search_content mention content...
Agent calls: search_content(query="about page title")  ❌ Wrong!
```

**Problems**:

-   ❌ Vague descriptions don't differentiate similar tools
-   ❌ Missing parameter descriptions cause wrong argument types
-   ❌ No validation allows malformed inputs to reach execution
-   ❌ Inconsistent naming creates ambiguity

### Why This Matters

-   **Reliability**: Wrong tool selection fails the task silently
-   **Debugging**: Hard to trace why agent picked wrong tool
-   **User trust**: Confident-sounding wrong actions erode confidence
-   **Cost**: Wasted tokens on failed tool calls and retries

## Core Concept

### What Makes a Good Tool?

A well-designed tool has four properties:

```
┌─────────────────────────────────────────────────────────────┐
│                    TOOL ANATOMY                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  DESCRIPTION ──▶ When should the LLM use this tool?        │
│                  What does it do? What does it NOT do?      │
│                                                             │
│  INPUT SCHEMA ──▶ What parameters are required/optional?   │
│                   What types and constraints?               │
│                                                             │
│  OUTPUT FORMAT ──▶ What shape does the result have?        │
│                    How should errors be represented?        │
│                                                             │
│  EXECUTE ──▶ What happens when the tool is called?         │
│              Side effects? Idempotent?                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Key Principles

1. **Description is Selection**: The description determines when the LLM chooses this tool. Be specific about use cases and differentiate from similar tools.

2. **Schema is Contract**: The input schema is a contract between the LLM and your code. Validate strictly.

3. **Names are Identifiers**: Tool names should be unambiguous, namespaced, and follow conventions.

## Implementation Patterns

### Pattern 1: Comprehensive Tool Definition

**Use Case**: Every tool definition should follow this structure.

```typescript
import { tool } from "ai";
import { z } from "zod";

export const cms_pages_update = tool({
  description: `Update an existing page's metadata or content.

    USE THIS TOOL WHEN:
    - User wants to change page title, slug, or status
    - User wants to modify page content
    - User wants to publish or unpublish a page

    DO NOT USE WHEN:
    - Creating a new page (use cms_pages_create)
    - Searching for pages (use cms_pages_search)
    - Deleting a page (use cms_pages_delete)

    REQUIRES: Page must exist. Use cms_pages_get first if unsure.`,

  parameters: z.object({
    pageId: z.string()
      .uuid()
      .describe("UUID of the page to update"),

    title: z.string()
      .min(1).max(200)
      .optional()
      .describe("New page title (1-200 characters)"),

    slug: z.string()
      .regex(/^[a-z0-9-]+$/)
      .optional()
      .describe("URL slug (lowercase, hyphens only)"),

    status: z.enum(["draft", "published", "archived"])
      .optional()
      .describe("Publication status"),

    content: z.string()
      .optional()
      .describe("Markdown content body"),
  }),

  execute: async (input, { experimental_context }) => {
    const ctx = experimental_context as AgentContext;
    const result = await ctx.services.pages.update(input.pageId, input);
    return { success: true, page: result };
  },
});
```

**Pros**:
-   ✅ Clear when to use and when not to use
-   ✅ Type-safe parameters with validation
-   ✅ Descriptive parameter names

**Cons**:
-   ❌ Longer descriptions use more tokens
-   ❌ Requires upfront design effort

**When to Use**: Every production tool

### Pattern 2: Naming Conventions

**Use Case**: Consistent naming across all tools in a system.

**Namespace Pattern**: `service_resource_action`

```
cms_pages_get        ──▶ CMS service, pages resource, get action
cms_pages_create     ──▶ CMS service, pages resource, create action
cms_pages_update     ──▶ CMS service, pages resource, update action
cms_pages_delete     ──▶ CMS service, pages resource, delete action
cms_pages_search     ──▶ CMS service, pages resource, search action

storage_images_upload   ──▶ Storage service, images resource, upload action
storage_images_delete   ──▶ Storage service, images resource, delete action

users_profile_get       ──▶ Users service, profile resource, get action
users_permissions_update ──▶ Users service, permissions resource, update action
```

**Action Verbs**:

| Verb | Meaning | Example |
|------|---------|---------|
| `get` | Fetch single item by ID | `cms_pages_get` |
| `list` | Fetch multiple items | `cms_pages_list` |
| `search` | Query with filters | `cms_pages_search` |
| `create` | Create new item | `cms_pages_create` |
| `update` | Modify existing item | `cms_pages_update` |
| `delete` | Remove item | `cms_pages_delete` |
| `upload` | Upload file/binary | `storage_images_upload` |

**Parameter Suffixes** for filtered queries:
-   `_by_id`: `users_get_by_id`
-   `_by_slug`: `cms_pages_get_by_slug`
-   `_by_email`: `users_search_by_email`

**When to Use**: Any system with 5+ tools

### Pattern 3: Zod Schema Patterns

**Use Case**: Type-safe, validated tool inputs with helpful error messages.

**Comprehensive Schema Example**:

```typescript
const pageSearchSchema = z.object({
  // Required string with constraints
  query: z.string()
    .min(1, "Query cannot be empty")
    .max(100, "Query too long (max 100 chars)")
    .describe("Search query - matches title, slug, or content"),

  // Optional with default
  limit: z.number()
    .int()
    .min(1).max(50)
    .default(10)
    .describe("Maximum results to return (1-50, default 10)"),

  // Enum with default
  status: z.enum(["all", "draft", "published", "archived"])
    .default("all")
    .describe("Filter by publication status"),

  // Optional date range
  createdAfter: z.coerce.date()
    .optional()
    .describe("Filter to pages created after this date (ISO 8601)"),

  // Array with constraints
  tags: z.array(z.string())
    .max(10)
    .optional()
    .describe("Filter by tags (max 10)"),

  // Nested object
  sort: z.object({
    field: z.enum(["title", "created_at", "updated_at"]),
    order: z.enum(["asc", "desc"]).default("desc"),
  })
    .optional()
    .describe("Sort configuration"),
});

// Extract TypeScript type
type PageSearchInput = z.infer<typeof pageSearchSchema>;
```

**Common Zod Patterns**:

| Pattern | Use Case |
|---------|----------|
| `.uuid()` | Entity IDs |
| `.email()` | Email addresses |
| `.url()` | URLs |
| `.regex()` | Custom formats (slugs, codes) |
| `.min().max()` | Bounded strings/numbers |
| `.default()` | Optional with fallback |
| `.coerce.date()` | Parse ISO date strings |
| `.describe()` | LLM-readable descriptions |

**When to Use**: Every tool input schema

### Pattern 4: Output Standardization

**Use Case**: Consistent return format across all tools.

```typescript
// Standardized tool result type
type ToolResult<T> =
  | { success: true; data: T }
  | { success: false; error: string; code?: string };

// Success case
return {
  success: true,
  data: {
    id: page.id,
    title: page.title,
    updatedAt: page.updatedAt
  }
};

// Error case
return {
  success: false,
  error: "Page not found",
  code: "NOT_FOUND"
};
```

**Error Codes**:

| Code | Meaning | Recovery |
|------|---------|----------|
| `NOT_FOUND` | Resource doesn't exist | Create or use different ID |
| `VALIDATION_ERROR` | Invalid input | Check parameter constraints |
| `PERMISSION_DENIED` | No access | Escalate or use different resource |
| `CONFLICT` | State conflict (duplicate) | Use existing or rename |
| `RATE_LIMITED` | Too many requests | Wait and retry |

**When to Use**: Multi-tool systems needing consistent error handling

## Framework Integration

### AI SDK v6 Tool Definition

```typescript
import { tool } from "ai";
import { z } from "zod";

// Basic tool with execute
export const searchPages = tool({
  description: "Search pages by query string",
  parameters: z.object({
    query: z.string().describe("Search query"),
    limit: z.number().default(10).describe("Max results"),
  }),
  execute: async (input) => {
    const results = await db.pages.search(input.query, input.limit);
    return { success: true, data: results };
  },
});

// Tool without execute (for client-side handling)
export const confirmDelete = tool({
  description: "Confirm deletion of a resource",
  parameters: z.object({
    resourceType: z.enum(["page", "entry", "image"]),
    resourceId: z.string().uuid(),
  }),
  // No execute - handled by client
});
```

## When to Use This Pattern

### ✅ Use When:

1. **Building Production Agents**
    - Consistent tool design prevents selection errors
    - Schema validation catches invalid inputs

2. **Multiple Related Tools**
    - Namespacing and conventions prevent confusion
    - Descriptions differentiate similar tools

3. **Team Development**
    - Conventions enable consistent contributions
    - Type safety catches errors at compile time

### ❌ Don't Use When:

1. **Single-Purpose Scripts**
    - Overhead not justified for one-off tools
    - Simple function calls sufficient

2. **Rapid Prototyping**
    - Defer polish until patterns stabilize
    - Focus on core functionality first

### Decision Matrix

| Situation | Recommended Approach |
|-----------|---------------------|
| 1-3 tools | Basic definition, minimal conventions |
| 4-10 tools | Namespacing, basic Zod schemas |
| 10-20 tools | Full conventions, comprehensive schemas |
| 20+ tools | Add semantic discovery (see 8.3) |

## Production Best Practices

### 1. Description Quality Checklist

Every tool description should answer:
-   **WHAT**: What does this tool do?
-   **WHEN**: When should the LLM use it?
-   **NOT**: When should it NOT be used? (differentiate from similar tools)
-   **REQUIRES**: Any preconditions or dependencies?

**Impact**: 90%+ tool selection accuracy with clear descriptions

### 2. Parameter Descriptions Are Critical

The LLM reads parameter descriptions to understand what to pass. Vague descriptions cause wrong arguments.

```typescript
// ❌ Bad: No description
pageId: z.string()

// ❌ Bad: Obvious description
pageId: z.string().describe("The page ID")

// ✅ Good: Specific, actionable
pageId: z.string()
  .uuid()
  .describe("UUID of the page to update. Get from cms_pages_search or cms_pages_list")
```

**Impact**: Reduces parameter errors by 60%+

### 3. Common Pitfalls

#### ❌ Pitfall 1: Vague Descriptions

"Gets data" or "Updates content" don't differentiate tools.

**Solution**: Be specific about use cases. Include "USE WHEN" and "DO NOT USE WHEN" sections.

#### ❌ Pitfall 2: Missing Validation

Trusting LLM to send correct types without validation.

**Solution**: Always use Zod schemas. Enable strict mode in OpenAI for guaranteed schema compliance.

#### ❌ Pitfall 3: Inconsistent Naming

`getPage`, `fetch_user`, `searchContent` in same system.

**Solution**: Pick one convention (`service_resource_action`) and enforce it everywhere.

#### ❌ Pitfall 4: No Error Differentiation

All errors return generic "Something went wrong."

**Solution**: Use error codes. Return structured errors that help LLM understand what went wrong and how to recover.

## Key Takeaways

1. **Description determines selection**—invest time in clear, differentiated descriptions
2. **Zod schemas are contracts**—validate strictly, describe thoroughly
3. **Naming conventions prevent confusion**—use `service_resource_action` pattern
4. **Standardize outputs**—consistent success/error format across all tools
5. **Differentiate similar tools**—explicitly state when to use vs. not use

**Quick Implementation Checklist**:

-   [ ] Every tool has WHAT/WHEN/NOT/REQUIRES in description
-   [ ] Every parameter has `.describe()` with actionable guidance
-   [ ] Names follow `service_resource_action` convention
-   [ ] Outputs use consistent `{ success, data/error }` format
-   [ ] Error codes enable LLM recovery decisions
