# 8.2 Context Injection

Pass dependencies (database, services, user context) to tools via a context object injected at runtime—never use global singletons or module-level instantiation.

## Overview

Tools need access to databases, services, user context, and other dependencies. The naive approach—importing singletons or instantiating at module level—creates tight coupling, makes testing impossible, and breaks in multi-tenant environments.

Context injection solves this by passing all dependencies through a context object at runtime. Each tool invocation receives exactly the services it needs, scoped to the current request.

**Key Research Findings** (2024-2025):

-   **Testability**: Context injection enables isolated unit testing of tools
-   **Multi-tenancy**: Per-request context supports user-scoped data access
-   **Flexibility**: Swap implementations (mock DB, different providers) without changing tool code

**Date Verified**: 2026-01-03

## The Problem: Tools With Hidden Dependencies

### The Classic Challenge

A tool imports a database singleton directly. In development, it works fine. In production, multiple users share the same database connection. In tests, you can't mock the database because the import happens at module load time.

```typescript
// ❌ Anti-pattern: Global singleton import
import { db } from "@/server/db";  // Imported at module level

export const getPageTool = tool({
  description: "Get page by ID",
  parameters: z.object({ pageId: z.string() }),
  execute: async (input) => {
    // Hidden dependency on global `db`
    const page = await db.pages.findById(input.pageId);
    return { success: true, data: page };
  },
});
```

**Problems**:

-   ❌ **Tight coupling**: Tool depends on specific database implementation
-   ❌ **Untestable**: Can't mock `db` without complex module mocking
-   ❌ **Multi-tenant unsafe**: All users share same connection/context
-   ❌ **Hidden state**: Dependencies not visible in tool signature

### Why This Matters

-   **Testing**: Can't unit test tools in isolation
-   **Debugging**: Hidden dependencies make tracing failures harder
-   **Security**: User A might access User B's data in shared singletons
-   **Flexibility**: Can't swap implementations for different environments

## Core Concept

### What is Context Injection?

Context injection passes all required dependencies through an explicit context object provided at tool execution time.

```
Request arrives
     ↓
┌─────────────────────────────────────────┐
│        Build Context Object             │
│  ┌───────────────────────────────────┐  │
│  │ db: DrizzleDB (request-scoped)    │  │
│  │ services: ServiceContainer        │  │
│  │ user: { id, permissions }         │  │
│  │ logger: RequestLogger             │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────┐
│     Pass to Agent via experimental_     │
│            context parameter            │
└─────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────┐
│   Tool extracts dependencies from       │
│   context at execution time             │
└─────────────────────────────────────────┘
```

### Key Principles

1. **Explicit Dependencies**: Every dependency is visible in the context interface
2. **Request Scoping**: Context is built per-request, not shared globally
3. **Testability**: Inject mock context in tests
4. **Type Safety**: Context interface defines available services

## Implementation Patterns

### Pattern 1: AgentContext Interface

**Use Case**: Define the contract for what's available to all tools.

```typescript
// types/agent-context.ts
import { DrizzleDB } from "@/server/db";
import { ServiceContainer } from "@/server/services";
import { AgentLogger } from "@/server/logging";

export interface AgentContext {
  // Database access
  db: DrizzleDB;

  // Service layer
  services: ServiceContainer;

  // Current user info
  user: {
    id: string;
    email: string;
    permissions: string[];
  };

  // Request-scoped logger
  logger: AgentLogger;

  // Session info
  session: {
    id: string;
    startedAt: Date;
  };

  // Optional: Stream writer for progress updates
  writer?: StreamWriter;
}
```

**Pros**:
-   ✅ Type-safe access to all dependencies
-   ✅ Clear contract between tools and infrastructure
-   ✅ Enables autocomplete in IDE

**Cons**:
-   ❌ Interface must be updated when adding new services
-   ❌ Some overhead in context construction

**When to Use**: Every agent system with tools

### Pattern 2: Context Factory

**Use Case**: Build context per-request with proper scoping.

```typescript
// server/context/context-factory.ts
export async function createAgentContext(
  request: AgentRequest
): Promise<AgentContext> {
  // Get user from auth
  const user = await authService.getUser(request.userId);

  // Create request-scoped logger
  const logger = new AgentLogger({
    requestId: request.id,
    userId: user.id,
    sessionId: request.sessionId,
  });

  // Build context
  return {
    db: database,
    services: new ServiceContainer(database, logger),
    user: {
      id: user.id,
      email: user.email,
      permissions: user.permissions,
    },
    logger,
    session: {
      id: request.sessionId,
      startedAt: new Date(),
    },
  };
}

// Usage in route handler
app.post("/api/agent", async (req, res) => {
  const context = await createAgentContext(req);

  const result = await agent.generate({
    messages: req.body.messages,
    experimental_context: context,
  });

  return res.json(result);
});
```

**Pros**:
-   ✅ Consistent context construction
-   ✅ Request-scoped resources
-   ✅ Easy to extend with new services

**When to Use**: Production agent deployments

### Pattern 3: Tool Context Extraction

**Use Case**: Safely extract typed context inside tool execute function.

```typescript
export const cms_pages_get = tool({
  description: "Get a page by ID or slug",
  parameters: z.object({
    pageId: z.string().optional(),
    slug: z.string().optional(),
  }),
  execute: async (input, { experimental_context }) => {
    // Extract and type the context
    const ctx = experimental_context as AgentContext;

    // Use services from context
    const pageService = ctx.services.getPageService();
    ctx.logger.info("Fetching page", { input });

    // Query with user context for permissions
    const page = input.pageId
      ? await pageService.getById(input.pageId, ctx.user)
      : await pageService.getBySlug(input.slug!, ctx.user);

    if (!page) {
      ctx.logger.warn("Page not found", { input });
      return { success: false, error: "Page not found", code: "NOT_FOUND" };
    }

    return { success: true, data: page };
  },
});
```

**Key Pattern**: Always cast `experimental_context` to your `AgentContext` type for type safety.

### Pattern 4: Service Container

**Use Case**: Lazy-load services to avoid instantiating unused dependencies.

```typescript
// server/services/container.ts
export class ServiceContainer {
  private _pageService?: PageService;
  private _imageService?: ImageService;

  constructor(
    private db: DrizzleDB,
    private logger: AgentLogger
  ) {}

  getPageService(): PageService {
    if (!this._pageService) {
      this._pageService = new PageService(this.db, this.logger);
    }
    return this._pageService;
  }

  getImageService(): ImageService {
    if (!this._imageService) {
      this._imageService = new ImageService(this.db, this.logger);
    }
    return this._imageService;
  }

  // Add more services as needed
}
```

**Pros**:
-   ✅ Services only instantiated when used
-   ✅ Single place to manage service dependencies
-   ✅ Easy to add new services

**When to Use**: Systems with many services where not all are needed per request

## Framework Integration

### AI SDK v6 experimental_context

```typescript
import { ToolLoopAgent } from "ai";
import { openrouter } from "@openrouter/ai-sdk-provider";

// Define agent with tools
const cmsAgent = new ToolLoopAgent({
  model: openrouter.languageModel("anthropic/claude-sonnet-4"),
  instructions: "You are a CMS assistant...",
  tools: {
    cms_pages_get: getPageTool,
    cms_pages_update: updatePageTool,
    cms_sections_list: listSectionsTool,
  },
});

// Execute with context injection
async function handleAgentRequest(request: Request) {
  // Build context for this request
  const context = await createAgentContext(request);

  // Pass context to agent
  const result = await cmsAgent.generate({
    messages: request.messages,
    experimental_context: context,  // ← Injected here
  });

  return result;
}
```

### Streaming with Context

```typescript
import { createAgentUIStreamResponse } from "ai";

export async function POST(request: Request) {
  const { messages, sessionId } = await request.json();

  // Build context
  const context = await createAgentContext({
    sessionId,
    userId: getCurrentUserId(request),
  });

  // Stream with context

    agent: cmsAgent,
    messages,
    experimental_context: context,
  });
}
```

### NestJS Integration

```typescript
// agents/cms.agent.ts
import { Injectable, Scope } from "@nestjs/common";
import { ToolLoopAgent } from "ai";

@Injectable({ scope: Scope.REQUEST })
export class CmsAgentService {
  constructor(
    private readonly pageService: PageService,
    private readonly imageService: ImageService,
    private readonly logger: Logger,
  ) {}

  private buildContext(userId: string): AgentContext {
    return {
      db: this.pageService.db,
      services: {
        pages: this.pageService,
        images: this.imageService,
      },
      user: { id: userId },
      logger: this.logger,
    };
  }

  async generate(messages: Message[], userId: string) {
    const context = this.buildContext(userId);

    return await this.agent.generate({
      messages,
      experimental_context: context,
    });
  }
}
```

## When to Use This Pattern

### ✅ Use When:

1. **Multi-Tenant Applications**
    - Each user needs isolated data access
    - Per-request scoping prevents data leaks

2. **Testable Code**
    - Tools should be unit testable
    - Mock context enables isolated testing

3. **Multiple Environments**
    - Dev/staging/prod need different configurations
    - Context injection allows environment-specific services

### ❌ Don't Use When:

1. **Simple Scripts**
    - Single-user, single-environment
    - Global imports acceptable for simplicity

2. **Stateless Functions**
    - No dependencies on external services
    - Pure computation doesn't need context

### Decision Matrix

| Situation | Approach |
|-----------|----------|
| Single tool, single user | Global imports OK |
| Multiple tools, single user | Consider context for testability |
| Multi-tenant application | Context injection required |
| Production deployment | Context injection required |

## Production Best Practices

### 1. Type Your Context

Always define an `AgentContext` interface. Use TypeScript's type system to catch missing dependencies at compile time.

```typescript
// ❌ Bad: Untyped context
const ctx = experimental_context as any;
ctx.db.query(...);  // No type safety

// ✅ Good: Typed context
const ctx = experimental_context as AgentContext;
ctx.db.query(...);  // Full autocomplete and type checking
```

**Impact**: Catches errors at compile time, enables IDE autocomplete

### 2. Validate Context in Tools

Tools should fail fast if context is missing or malformed.

```typescript
execute: async (input, { experimental_context }) => {
  const ctx = experimental_context as AgentContext | undefined;

  if (!ctx?.db || !ctx?.user) {
    throw new Error("Tool requires AgentContext with db and user");
  }

  // Proceed with validated context
  const result = await ctx.db.pages.findById(input.pageId);
  // ...
}
```

**Impact**: Clear error messages when context is misconfigured

### 3. Common Pitfalls

#### ❌ Pitfall 1: Module-Level Service Instantiation

```typescript
// ❌ Bad: Service created at module load
const pageService = new PageService(database);

export const getPageTool = tool({
  execute: async (input) => {
    return pageService.getPage(input.id);  // Shared across all requests
  },
});
```

**Solution**: Create services in context factory, inject via experimental_context.

#### ❌ Pitfall 2: Closures Over Request Data

```typescript
// ❌ Bad: Closure captures stale userId
function createTool(userId: string) {
  return tool({
    execute: async (input) => {
      // userId captured at tool creation time, not execution time
      return db.pages.findByUser(userId);
    },
  });
}
```

**Solution**: Pass user info in context, read at execution time.

#### ❌ Pitfall 3: Missing Context in Tests

```typescript
// ❌ Bad: Test without context
const result = await getPageTool.execute({ pageId: "123" });
// Fails: experimental_context is undefined

// ✅ Good: Test with mock context
const mockContext: AgentContext = {
  db: mockDb,
  services: mockServices,
  user: { id: "test-user", permissions: ["read"] },
  logger: mockLogger,
};

const result = await getPageTool.execute(
  { pageId: "123" },
  { experimental_context: mockContext }
);
```

**Impact**: Enables proper unit testing of tools

## Key Takeaways

1. **Never use global singletons** in tools—inject dependencies via context
2. **Define AgentContext interface**—type safety catches errors at compile time
3. **Build context per-request**—enables multi-tenancy and proper scoping
4. **Use context factory**—consistent construction across all routes
5. **Validate context in tools**—fail fast with clear errors if misconfigured

**Quick Implementation Checklist**:

-   [ ] Define `AgentContext` interface with all required services
-   [ ] Create `createAgentContext()` factory function
-   [ ] Pass context via `experimental_context` parameter
-   [ ] Cast to `AgentContext` in tool execute functions
-   [ ] Write tests with mock context objects
