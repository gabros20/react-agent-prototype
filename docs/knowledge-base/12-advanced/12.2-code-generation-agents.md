## Overview

Code generation agents represent a paradigm shift from autocomplete to autonomous software engineering. Unlike simple code completion (GitHub Copilot), these agents:

1. **Understand context** across entire repositories, not just open files
2. **Plan before coding** - decompose tasks into steps before writing code
3. **Execute and test** - run code, observe failures, iterate
4. **Edit multiple files** - coordinate changes across a codebase
5. **Self-correct** - use test feedback to fix their own mistakes

The key innovation is the **Code-Test-Fix loop**: agents don't just generate code once, they iterate until tests pass.

**Key Research Findings** (2024-2025):

- **SWE-Agent**: 26.3% resolve rate on SWE-Bench (real GitHub issues)
- **Claude 3.5 Sonnet**: 49% on SWE-Bench Verified (human-validated subset)
- **OpenHands**: Open-source platform achieving competitive results
- **Aider**: 72% on Exercism exercises with diff-based editing

**Date Verified**: January 2026

## The Problem: Code Generation at Scale

### The Classic Challenge

Single-shot code generation fails on real-world tasks that require understanding context, testing, and iteration.

```
Traditional LLM Code Generation:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

User: "Fix the login bug in auth.py"
       ↓
LLM: [Generates code patch]
       ↓
Result: ❌ Patch doesn't apply (wrong line numbers)
        ❌ Missing import statement
        ❌ Breaks existing tests
        ❌ Doesn't match code style
```

**Problems**:

- ❌ **Context blindness**: LLM doesn't see full codebase
- ❌ **No verification**: Generated code isn't tested
- ❌ **One-shot failure**: No retry on errors
- ❌ **Integration gaps**: Changes don't fit existing patterns

### Why This Matters

Real software engineering requires:

- Reading and understanding existing code
- Making changes that fit project conventions
- Running tests to verify correctness
- Iterating until the solution works

Single-shot generation addresses none of these. Code agents close this gap.

### Key Principles

1. **Repository as context**: Agent has access to full codebase, not just snippets
2. **Tool-mediated execution**: Agent uses tools, doesn't just generate text

4. **Sandboxed execution**: Code runs in isolated environments for safety

## Implementation Patterns

### Pattern 1: SWE-Agent Architecture

**Use Case**: Autonomous bug fixing and feature implementation on real codebases.

SWE-Agent's key innovation is the **Agent-Computer Interface (ACI)** - a specialized set of tools designed for code editing that are easier for LLMs to use than raw bash commands.

```
┌─────────────────────────────────────────────────────────┐
│            SWE-AGENT ACI DESIGN                         │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Problem: Raw bash is error-prone for LLMs             │
│  ❌ cat file.py | head -50          (hard to parse)    │
│  ❌ sed -i 's/old/new/' file.py     (regex errors)     │
│                                                         │
│  Solution: Purpose-built commands                       │
│  ✅ open file.py                    (shows with lines) │
│  ✅ edit 15:20 "new code"           (structured edit)  │
│  ✅ search_dir "pattern" ./src      (formatted output) │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**Core Tools**:

```typescript
const sweAgentTools = {
```

**Pros**:

- ✅ 26.3% on SWE-Bench (vs 3.8% for raw GPT-4)
- ✅ Designed for LLM usability
- ✅ Structured output format reduces parsing errors

**Cons**:

- ❌ Custom tooling required
- ❌ Learning curve for new interfaces
- ❌ May not match human workflows

**When to Use**: Autonomous bug fixing, GitHub issue resolution.

### Pattern 2: Diff-Based Editing (Aider)

**Use Case**: Interactive coding with minimal token usage.

Aider's innovation is using **unified diffs** for edits - the same format used by `git diff`. This is token-efficient and familiar to developers.

```
Aider Diff Format:
━━━━━━━━━━━━━━━━━━

<<<<<<< SEARCH
def old_function():
    return "old"
=======
def new_function():
    return "new"
>>>>>>> REPLACE
```

```typescript
// Parse and apply Aider-style diffs
function applyAiderDiff(content: string, diff: string): string {
  const searchMatch = diff.match(/<<<<<<< SEARCH\n([\s\S]*?)\n=======/);
  const replaceMatch = diff.match(/=======\n([\s\S]*?)\n>>>>>>> REPLACE/);

  if (!searchMatch || !replaceMatch) {
    throw new Error("Invalid diff format");
  }

  const search = searchMatch[1];
  const replace = replaceMatch[1];

  if (!content.includes(search)) {
    throw new Error(`Search block not found in file`);
  }

  return content.replace(search, replace);
}
```

**Pros**:

- ✅ 72% on Exercism exercises
- ✅ Token-efficient (only changed lines sent)
- ✅ Human-readable format
- ✅ Easy to review before applying

**Cons**:

- ❌ Requires exact match of search block
- ❌ Fails if code has been modified
- ❌ Single-file focus

**When to Use**: Interactive coding sessions, pair programming with AI.

### Pattern 3: Multi-File Orchestration

**Use Case**: Features requiring changes across multiple files.

Real features touch multiple files: component, tests, types, styles. This pattern coordinates multi-file changes.

```
┌─────────────────────────────────────────────────────────┐
│           MULTI-FILE EDIT WORKFLOW                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Task: "Add user profile page"                          │
│                                                         │
│  Step 1: PLAN                                           │
│  ├─ Identify affected files                             │
│  ├─ Determine edit order (types → impl → tests)         │
│  └─ Check for conflicts                                 │
│                                                         │
│  Step 2: EDIT (in order)                                │
│  ├─ types/user.ts        (add Profile type)             │
│  ├─ components/Profile.tsx (create component)           │
│  ├─ pages/profile.tsx    (create page)                  │
│  ├─ routes.ts            (add route)                    │
│  └─ tests/profile.test.ts (add tests)                   │
│                                                         │
│  Step 3: VALIDATE                                       │
│  ├─ TypeScript compile (catch type errors)              │
│  ├─ Lint check (style consistency)                      │
│  └─ Run tests (functional correctness)                  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

```typescript
interface MultiFileEditPlan {
  files: {
    path: string;
    operation: "create" | "modify" | "delete";
    dependencies: string[]; // Files that must be edited first
    changes: string; // Description of changes
  }[];
  validationSteps: string[]; // Commands to run after editing
}

async function executeMultiFileEdit(plan: MultiFileEditPlan) {
  // Sort by dependencies (topological sort)
  const orderedFiles = topologicalSort(plan.files);

  for (const file of orderedFiles) {
    // Edit file
    await agent.editFile(file.path, file.changes);

    // Quick validation after each file
    const result = await runCommand("tsc --noEmit");
    if (!result.success) {
      // Self-correct before continuing
      await agent.fixTypeErrors(result.errors);
    }
  }

  // Final validation
  for (const step of plan.validationSteps) {
    await runCommand(step);
  }
}
```

**Pros**:

- ✅ Handles real-world feature complexity
- ✅ Catches errors early (per-file validation)
- ✅ Respects dependency order

**Cons**:

- ❌ More complex orchestration
- ❌ Partial failures require rollback
- ❌ Longer execution time

**When to Use**: Feature development, refactoring, migration tasks.

### Pattern 4: Sandboxed Execution (E2B/Modal)

**Use Case**: Safe code execution in isolated environments.

Running LLM-generated code in production environments is dangerous. Sandboxing isolates execution.

```
┌─────────────────────────────────────────────────────────┐
│              SANDBOX ARCHITECTURE                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────────────────────────────────────────────┐   │
│  │              HOST SYSTEM                         │   │
│  │                                                  │   │
│  │   Agent Core ──────┬──────► E2B/Modal API       │   │
│  │                    │                             │   │
│  └────────────────────┼────────────────────────────┘   │
│                       │                                 │
│                       ▼                                 │
│  ┌──────────────────────────────────────────────────┐   │
│  │         ISOLATED SANDBOX (Firecracker VM)        │   │
│  │  ┌────────────────────────────────────────────┐  │   │
│  │  │  • Cloned repository                       │  │   │
│  │  │  • Installed dependencies                  │  │   │
│  │  │  • Time-limited execution                  │  │   │
│  │  │  • Network restricted (optional)           │  │   │
│  │  │  • Resource limits (CPU/memory)            │  │   │
│  │  └────────────────────────────────────────────┘  │   │
│  │                                                  │   │
│  │  Destroyed after use ──► No persistent state    │   │
│  └──────────────────────────────────────────────────┘   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

```typescript
import { E2B } from "@e2b/sdk";

async function runInSandbox(code: string, language: string) {
  const sandbox = await E2B.create({
    template: "python", // or 'node', 'go', etc.
    timeout: 60000, // 60 second limit
    metadata: { task: "code-execution" },
  });

  try {
    // Execute code
    const result = await sandbox.runCode(code, {
      language,
      onStdout: (data) => console.log(data),
      onStderr: (data) => console.error(data),
    });

    return {
      success: result.exitCode === 0,
      stdout: result.stdout,
      stderr: result.stderr,
    };
  } finally {
    // Always destroy sandbox
    await sandbox.destroy();
  }
}
```

**Sandbox Providers**:

| Provider       | Isolation     | Cold Start | Best For                |
| -------------- | ------------- | ---------- | ----------------------- |
| **E2B**        | Firecracker   | ~200ms     | Code execution, testing |
| **Modal**      | gVisor        | ~500ms     | Heavy compute, GPUs     |
| **Docker**     | Containers    | ~1-2s      | Self-hosted, custom     |
| **Fly.io**     | Firecracker   | ~300ms     | Edge execution          |

**Pros**:

- ✅ Complete isolation from host
- ✅ Automatic cleanup
- ✅ Resource limits prevent runaway

**Cons**:

- ❌ Cold start latency
- ❌ Cost per execution
- ❌ Network restrictions may limit functionality

**When to Use**: Any production code agent that executes LLM-generated code.

## Framework Integration

### AI SDK v6 Code Agent

```typescript
import { agent, tool } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const codeAgent = agent({
  model: openai("gpt-4o"),
  system: `You are a code agent that can read, write, and execute code.
Follow these steps for every task:
1. Read relevant files to understand context
2. Plan your changes
3. Make edits
4. Run tests to verify
5. Fix any failures

Always run tests before considering a task complete.`,
  tools: {
    readFile: tool({
      description: "Read a file from the repository",
      parameters: z.object({ path: z.string() }),
      execute: async ({ path }) => {
        return await fs.readFile(path, "utf-8");
      },
    }),

    writeFile: tool({
      description: "Write content to a file",
      parameters: z.object({
        path: z.string(),
        content: z.string(),
      }),
      execute: async ({ path, content }) => {
        await fs.writeFile(path, content);
        return { success: true };
      },
    }),

    runCommand: tool({
      description: "Run a shell command (use for tests, linting)",
      parameters: z.object({ command: z.string() }),
      execute: async ({ command }, { experimental_context }) => {
        // Execute in sandbox
        const result = await experimental_context.sandbox.exec(command);
        return {
          exitCode: result.exitCode,
          stdout: result.stdout,
          stderr: result.stderr,
        };
      },
    }),

    searchCode: tool({
      description: "Search for code patterns in the repository",
      parameters: z.object({
        pattern: z.string(),
        fileType: z.string().optional(),
      }),
      execute: async ({ pattern, fileType }) => {
        const glob = fileType ? `**/*.${fileType}` : "**/*";
        return await grep(pattern, glob);
      },
    }),
  },
  maxSteps: 20, // Allow iteration
});

// Usage
const result = await codeAgent.generate({
  prompt: "Fix the failing test in auth.test.ts",
});
```

### Test-Driven Code Agent

```typescript
// Agent that uses tests as success criteria
const testDrivenAgent = agent({
  model: openai("gpt-4o"),
  system: `You are a test-driven code agent.

Your workflow:
1. First, run the existing tests to see what's failing
2. Read the failing test to understand what's expected
3. Read the implementation file
4. Fix the code to make the test pass
5. Run tests again to verify
6. If tests still fail, analyze the error and try again

NEVER claim success without running tests.`,
  tools: {
    /* ... same tools as above ... */
  },

  // Custom step handler for test-driven loop
  onStepFinish: async ({ step, state }) => {
    // After each code change, automatically run tests
    if (step.toolCalls.some((t) => t.name === "writeFile")) {
      const testResult = await runTests();
      if (!testResult.success) {
        // Inject test failure into context for next step
        state.messages.push({
          role: "system",
          content: `Tests failed:\n${testResult.stderr}`,
        });
      }
    }
  },
});
```

## When to Use This Pattern

### ✅ Use When:

1. **Automated bug fixing**
   - Clear reproduction steps or failing tests
   - Well-tested codebase
   - Example: GitHub issue resolution, CI failure fixes

2. **Repetitive code tasks**
   - Migration scripts (upgrade library versions)
   - Boilerplate generation
   - Example: Add TypeScript types to JS files

3. **Interactive development**
   - Pair programming with AI
   - Prototyping with immediate feedback
   - Example: Cursor, Windsurf workflows

### ❌ Don't Use When:

1. **Architectural decisions**
   - Requires deep system understanding
   - Trade-offs need human judgment
   - Better alternative: Use for implementation after human designs

2. **Security-critical code**
   - LLMs can introduce vulnerabilities
   - Risk too high for autonomous execution
   - Better alternative: Generate suggestions for human review

3. **Untested codebases**
   - No way to verify correctness
   - Agent can't know if changes break things
   - Better alternative: Add tests first, then use code agent

### Decision Matrix

| Your Situation           | Recommended Approach                  |
| ------------------------ | ------------------------------------- |
| Fix failing CI           | Full code agent with test loop        |
| Add new feature          | Plan with human, implement with agent |
| Refactor function        | Diff-based editing (Aider-style)      |

## Production Best Practices

### 1. Always Sandbox Execution

Never run LLM-generated code in production environment.

```typescript
// Bad: Direct execution
await exec(llmGeneratedCommand); // 🚨 Dangerous

// Good: Sandboxed execution
await sandbox.exec(llmGeneratedCommand); // ✅ Safe
```

**Why**: LLM can generate `rm -rf /` or exfiltrate data.
**Impact**: Prevents catastrophic failures.

### 2. Require Test Validation

Don't trust LLM's claim that code is correct.

```typescript
const result = await codeAgent.generate({ prompt: task });

// Don't trust: result.text says "I fixed the bug"
// Do trust: test execution results
const testResult = await runTests();
if (!testResult.success) {
  // Agent didn't actually fix it
  await codeAgent.generate({
    prompt: `Tests still failing: ${testResult.stderr}`,
  });
}
```

**Why**: LLMs confidently claim success even when wrong.
**Impact**: Catches 40%+ of false "completions".

### 3. Limit Iteration Budget

Set hard caps on attempts and tokens.

```typescript
const config = {
  maxSteps: 20, // Max tool calls
  maxAttempts: 5, // Max retry cycles
  maxTokens: 100000, // Budget cap
  timeout: 300000, // 5 minute limit
};
```

**Why**: Prevents runaway costs on hard tasks.
**Impact**: 80% cost reduction on failing tasks.

### 4. Common Pitfalls

#### ❌ Pitfall 1: Insufficient context

Agent edits code without understanding the full picture.

**Problem**: Changes break other parts of the codebase.

#### ✅ Solution: Force context gathering

```typescript
// In system prompt
`Before editing any file, you MUST:
1. Search for usages of the function/class you're modifying
2. Read related test files
3. Check for type definitions
Only then proceed with edits.`;
```

**Benefit**: 50% reduction in breaking changes.

### Testing Approach

**What to Test**:

- Does agent correctly parse tool outputs?
- Does agent stop when tests pass?
- Does agent handle permission errors gracefully?

```typescript
test("agent stops after tests pass", async () => {
  const mockTests = jest.fn().mockResolvedValueOnce({ pass: false }).mockResolvedValueOnce({ pass: true });

  await codeAgent.run(task, { runTests: mockTests });

  expect(mockTests).toHaveBeenCalledTimes(2);
  // Agent should stop after second call (tests passed)
});
```

### Common Failure Modes

1. **Edit collision**: Agent edits same lines multiple times
   - **Detection**: Track edit locations, alert on overlaps
   - **Mitigation**: Merge conflicting edits before applying

2. **Test flakiness**: Passing tests fail on retry
   - **Detection**: Run tests multiple times
   - **Mitigation**: Mark flaky tests, don't trust single run

3. **Context overflow**: Repository too large for context
   - **Detection**: Token count exceeds limit
   - **Mitigation**: Intelligent file selection, chunking

## Trade-offs & Considerations

### Advantages

1. **Autonomy**: Handles end-to-end tasks without constant input
2. **Speed**: Faster than human for repetitive changes
3. **Consistency**: Applies same patterns across files

### Disadvantages

1. **Reliability**: Still fails on complex tasks (50-75% failure rate)
2. **Cost**: Iteration is expensive ($1-10 per task)
3. **Trust**: Requires verification of every output

- Agent success (70%): 70 bugs × $5 = $350
- Agent failure + human: 30 bugs × $150 = $4,500
- Human review time: 100 bugs × 15 min = 25 hours × $75 = $1,875
- **Total**: $6,725/month
- **Savings**: 55%

## Key Takeaways

1. **Tools make the difference** - Raw LLMs achieve 3.8%, agents achieve 26%+
2. **Tests are the oracle** - Never trust LLM's claim, verify with tests
3. **Sandbox everything** - LLM-generated code execution is inherently risky
4. **Iteration is expected** - Successful solutions average 3-7 attempts
5. **Human review remains critical** - Agents augment, don't replace
