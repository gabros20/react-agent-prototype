# 11.2 Debugging Techniques

## TL;DR

AI agents are non-deterministic—traditional debugging fails. Use checkpoint-based replay to reproduce issues, step-by-step execution to isolate failures, and state visualization to understand reasoning chains. Time-travel debugging is essential for production agent systems.

## Overview

Debugging AI agents differs fundamentally from traditional software. Agents are probabilistic, stateful across multiple steps, and sensitive to context. A bug that appears once may never reproduce with the same inputs because LLM outputs vary.

The solution: **checkpoint-based replay** and **time-travel debugging**. Capture complete agent state at each step, then replay from any checkpoint to inspect, modify, and re-execute.

**Key Research Findings** (2024-2025):

-   **30-35% success rate** for multi-step agent tasks without debugging infrastructure (CMU/Salesforce 2024)
-   **80% reduction** in debugging time with visual trace inspection (Agent Prism)
-   **89% of organizations** now implement agent observability; 62% have step-level tracing
-   **Time-travel debugging** adopted by OpenAI Codex via Temporal for production reliability

**Date Verified**: 2026-01-04

## The Problem: Non-Deterministic Failures

### The Classic Challenge

A user reports that the agent "gave a wrong answer." You try to reproduce:

```
Production (Tuesday 2pm):
  User: "What's the status of order #12345?"
  Agent: "Your order was cancelled" ← WRONG (order was delivered)

Debug Attempt (Tuesday 3pm):
  Developer: "What's the status of order #12345?"
  Agent: "Your order was delivered yesterday" ← CORRECT

Why different? You can't reproduce. You can't debug.
```

**Root Causes**:
- LLM temperature introduces randomness
- Context window contained different information
- Tool returned different data (database changed)
- Model weights updated by provider

**Problems**:

-   ❌ **Non-reproducible**: Same input → different output
-   ❌ **State invisible**: Can't see agent's "reasoning" at failure time
-   ❌ **No replay**: Can't re-run from exact production state
-   ❌ **Compound errors**: Early mistakes cascade through multi-step flows

### Why This Matters

-   **Debugging cost**: Engineers spend hours on issues that should take minutes
-   **User trust**: Unexplainable failures erode confidence
-   **Regression detection**: Can't verify fixes without reproduction
-   **Root cause analysis**: Impossible without state visibility

### Checkpoint Components

A complete checkpoint captures everything needed for deterministic replay:

```
Checkpoint {
  // Identification
  checkpointId: "chk-abc-123",
  traceId: "trace-xyz-789",
  stepNumber: 3,
  timestamp: "2026-01-04T10:30:45Z",

  // Agent State
  state: {
    messages: [...],        // Full conversation history
    variables: {...},       // Working memory
    currentTool: "search",  // Tool being executed
    toolResults: [...],     // Previous tool outputs
  },

  // Execution Context
  context: {
    model: "gpt-4o-2024-11-20",  // Exact model version
    temperature: 0.7,
    maxTokens: 4096,
    systemPrompt: "...",
  },

  // External State (for replay)
  externalState: {
    toolResponses: {...},   // Cached API responses
    dbSnapshots: {...},     // Relevant DB state
    timestamps: {...},      // For time-dependent logic
  }
}
```

### Key Principles

1. **Checkpoint after every step**: State must persist before continuing
2. **Capture external state**: API responses, DB queries must be replayable
3. **Version everything**: Model ID, prompt versions, tool versions
4. **Structured output only**: Free-form parsing breaks determinism

## Implementation Patterns

### Pattern 1: Checkpoint-Based Replay

**Use Case**: Reproduce any production issue by loading exact state from failure point.

**Architecture**:

```
┌─────────────────────────────────────────────────────────────┐
│               CHECKPOINT REPLAY SYSTEM                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Production                                                 │
│  ──────────                                                 │
│  Agent executes → Checkpoint after each step → Store        │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ Checkpoint Storage                                   │   │
│  │ ├── SQLite (development)                            │   │
│  │ ├── PostgreSQL (production)                         │   │
│  │ └── Redis (high-throughput)                         │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Debug Session                                              │
│  ─────────────                                              │
│  1. Query: Find checkpoint by traceId + stepNumber         │
│  2. Load: Deserialize complete agent state                 │
│  3. Inspect: View state, prompt, tool calls                │
│  4. Modify: Edit state or prompt                           │
│  5. Continue: Execute from checkpoint                      │
│  6. Fork: Create alternative execution branch              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Replay Modes**:

| Mode | Description | Use Case |
|------|-------------|----------|
| **Inspect Only** | Load state, view without executing | Understanding failures |
| **Continue** | Resume execution from checkpoint | Testing fixes |
| **Fork** | Branch from checkpoint, explore alternatives | A/B testing decisions |
| **Modify & Replay** | Edit state, then execute | What-if analysis |

**Pros**:
-   ✅ Deterministic reproduction of any issue
-   ✅ Enables "what-if" debugging
-   ✅ Supports A/B testing agent decisions

**Cons**:
-   ❌ Storage overhead for checkpoints
-   ❌ External API state hard to capture perfectly
-   ❌ Privacy concerns with stored prompts

### Pattern 2: Step-by-Step Execution

**Use Case**: Debug agent reasoning by pausing after each step.

**Implementation**:

```
┌─────────────────────────────────────────────────────────────┐
│              STEP-BY-STEP DEBUG MODE                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Debug Controls                                             │
│  ──────────────                                             │
│  [▶ Run] [⏸ Pause] [⏭ Step] [⏹ Stop] [↩ Reset]            │
│                                                             │
│  Current Step: 3 / 7                                        │
│  ────────────────────                                       │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ Step Type: tool_call                                 │   │
│  │ Tool: search_database                               │   │
│  │ Input: { "query": "order #12345" }                  │   │
│  │ Status: PAUSED (waiting for continue)               │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  State Inspector                                            │
│  ───────────────                                            │
│  ├── Messages (5)                                          │
│  │   └── [Expand to view conversation]                     │
│  ├── Working Memory                                        │
│  │   └── orderId: "12345", status: "pending"              │
│  └── Tool Results (2)                                      │
│      └── [Expand to view previous results]                 │
│                                                             │
│  Actions                                                    │
│  ───────                                                    │
│  [Edit State] [Skip Step] [Inject Response] [Continue]     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Interrupt Points**:
| Point | Description |
|-------|-------------|
| **Before LLM call** | Inspect prompt before sending |
| **After LLM call** | View response before tool execution |
| **Before tool call** | Check tool input parameters |
| **After tool call** | Verify tool output |
| **State transition** | Inspect state changes |

**Pros**:
-   ✅ Fine-grained control over execution
-   ✅ Immediate feedback on each decision
-   ✅ Can modify state mid-execution

**Cons**:
-   ❌ Slow for long workflows
-   ❌ May miss timing-dependent bugs
-   ❌ Requires interactive session

### Pattern 3: LLM Call Inspection

**Use Case**: Understand exactly what the model saw and why it responded that way.

**What to Capture**:

```
LLM Call Record {
  // Request
  request: {
    model: "gpt-4o-2024-11-20",
    messages: [
      { role: "system", content: "..." },
      { role: "user", content: "..." },
      { role: "assistant", content: "...", tool_calls: [...] },
      { role: "tool", content: "...", tool_call_id: "..." },
    ],
    tools: [...],
    temperature: 0.7,
    max_tokens: 4096,
  },

  // Response
  response: {
    content: "Based on the search results...",
    tool_calls: [{ name: "get_order", arguments: {...} }],
    finish_reason: "tool_calls",
    usage: { input: 1500, output: 150, cached: 800 },
  },

  // Metadata
  metadata: {
    latency_ms: 1234,
    cost_usd: 0.045,
    provider_request_id: "req-xyz",
    cache_hit: true,
  }
}
```

**Inspection Checklist**:
| Check | What to Look For |
|-------|------------------|
| **System prompt** | Missing instructions? Conflicting guidance? |
| **Context window** | Truncated? Missing critical info? |
| **Tool definitions** | Clear descriptions? Correct schemas? |
| **Previous messages** | Lost context? Wrong order? |
| **Token usage** | Near limit? Truncation risk? |
| **Temperature** | Too random? Too deterministic? |

**Pros**:
-   ✅ Complete visibility into model input/output
-   ✅ Identifies prompt engineering issues
-   ✅ Catches context window problems

**Cons**:
-   ❌ Large data volume for long conversations
-   ❌ PII exposure risk

## When to Use This Pattern

### ✅ Use When:

1. **Production Debugging**
   - User-reported issues that can't be reproduced
   - Intermittent failures in multi-step workflows
   - Performance investigations

2. **Development Iteration**
   - Testing prompt changes
   - Validating tool integrations
   - Exploring agent behavior

3. **Quality Assurance**
   - Regression testing after changes
   - Verifying fixes address root cause
   - A/B testing agent configurations

### ❌ Don't Use When:

1. **Simple Errors**
   - Clear error messages with obvious fixes
   - Single-step operations
   - Deterministic failures

2. **Performance Testing**
   - Checkpoint overhead affects benchmarks
   - Use sampling for performance analysis instead

### Decision Matrix

| Situation | Recommended Approach |
|-----------|---------------------|
| Production bug report | Load checkpoint, inspect state |
| Intermittent failure | Enable full checkpointing, wait for occurrence |
| Prompt optimization | Fork from checkpoint, A/B test |
| New tool integration | Step-by-step execution |
| Understanding flow | State visualization |

## Production Best Practices

### 1. Checkpoint Storage Strategy

**Development**: SQLite—fast, local, no setup

**Production**: PostgreSQL—durable, queryable, team-accessible

**High-Volume**: Redis with TTL—fast writes, automatic expiration

**Retention Policy**:
| Type | Retention |
|------|-----------|
| Successful traces | 7 days |
| Failed traces | 30 days |
| User-flagged | 90 days |
| Compliance-required | Per policy |

### 2. Deterministic Replay Requirements

For reliable replay, enforce:

**Structured Output**: LLM must return structured JSON, not free-form text that requires parsing.

**Capture External State**: Cache all API responses, database queries, and time-dependent values.

**Version Pinning**: Record exact model version (e.g., `gpt-4o-2024-11-20`), not just model family.

**Seed Control**: Use consistent random seeds where supported.

### 3. Common Pitfalls

#### ❌ Pitfall 1: Checkpointing Too Infrequently

Checkpointing only at task completion loses debugging granularity.

**Problem**: Failure at step 8 of 10, but only checkpoint at step 1 and step 10.

**Solution**: Checkpoint after every step. Storage is cheap; debugging time is expensive.

#### ❌ Pitfall 2: Missing External State

Replay fails because external API returns different data.

**Problem**: Production trace shows tool returned `{"status": "delivered"}`, but replay shows `{"status": "shipped"}` because database changed.

**Solution**: Cache external responses in checkpoint. Mock external calls during replay using cached data.

#### ❌ Pitfall 3: Free-Form Tool Calls

Agent returns tool call as natural language, parsed heuristically.

**Problem**: `"I'll search for order 12345"` parsed differently across runs.

**Solution**: Enforce strict JSON tool calls. Use Zod schemas for validation.

### 4. Debug Workflow Template

```
1. IDENTIFY
   └── Find problematic trace via logs/alerts/user report

2. LOCATE
   └── Query checkpoints by traceId
   └── Identify step where behavior diverged

3. INSPECT
   └── Load checkpoint at divergence point
   └── Examine: state, prompt, tool calls, LLM response

4. HYPOTHESIZE
   └── Form theory: prompt issue? tool bug? context truncation?

5. TEST
   └── Fork from checkpoint
   └── Modify state or prompt
   └── Execute and observe

6. FIX
   └── Implement fix in codebase
   └── Replay original trace with fix
   └── Verify correct behavior

7. PREVENT
   └── Add test case for failure scenario
   └── Update monitoring/alerts
   └── Document in runbook
```

## Key Takeaways

1. **Time-travel debugging is essential**—non-deterministic agents require checkpoint-based replay
2. **Checkpoint after every step**—storage is cheap; debugging time is expensive
3. **Capture external state**—API responses, DB queries must be replayable
4. **Use structured output only**—free-form parsing breaks determinism
5. **Version everything**—exact model ID, prompt version, tool versions

**Quick Implementation Checklist**:

-   [ ] Implement checkpoint storage (SQLite for dev, PostgreSQL for prod)
-   [ ] Checkpoint after every agent step
-   [ ] Capture complete state: messages, variables, tool results

-   [ ] Build or integrate state visualization
