## Overview

Multi-agent orchestration divides complex tasks among specialized agents, each with focused capabilities and tools. Instead of one agent with 50 tools, you deploy five agents with 10 tools each—improving reliability, maintainability, and task performance.

The orchestrator (supervisor) analyzes incoming requests, routes to appropriate specialists, manages context transfer, and assembles final responses. This pattern mirrors how human teams work: a manager delegates to specialists rather than doing everything themselves.

**Key Research Findings** (2024-2025):

-   **88% vs 50% accuracy** on strategic reasoning tasks (multi-agent vs single agent)
-   **3x latency and cost** overhead for multi-agent systems
-   **Agent with 5 tools > agent with 50 tools** for reliability (focused specialists win)
-   **Misrouted requests cascade** through incorrect agents, compounding errors

**Date Verified**: 2026-01-04

## The Problem: Agents That Do Too Much

### The Classic Challenge

A single agent handles everything—research, calculations, writing, code generation, data analysis. As capabilities grow, the agent becomes unreliable:

```
Single Agent Architecture:
┌─────────────────────────────────────────┐
│            MONOLITHIC AGENT             │
│                                         │
│  Tools: search, calculate, write,       │
│         code, analyze, format,          │
│         translate, summarize,           │
│         ... (50+ tools)                 │
│                                         │
│  Problems:                              │
│  - Confused tool selection              │
│  - Context window overflow              │
│  - Hallucinated capabilities            │
│  - Unpredictable behavior               │
└─────────────────────────────────────────┘
```

**Problems**:

-   ❌ **Tool confusion**: Agent selects wrong tool from 50+ options (selection accuracy drops with tool count)
-   ❌ **Context overflow**: System prompt with all tool descriptions consumes 80% of context
-   ❌ **Capability hallucination**: Agent claims abilities it doesn't have
-   ❌ **Debugging nightmare**: Hard to isolate failures in monolithic system

### Why This Matters

-   **Reliability**: 50-tool agents fail unpredictably; 5-tool agents fail predictably
-   **Maintainability**: Adding a tool to monolithic agent risks breaking everything
-   **Cost**: Wasted tokens on irrelevant tool descriptions every request
-   **User trust**: Inconsistent behavior erodes confidence

## Core Concept

### What is Multi-Agent Orchestration?

Multi-agent orchestration coordinates multiple specialized agents through a supervisor that:

1. **Classifies intent** from user requests
2. **Routes to specialists** based on capabilities
3. **Transfers context** between agents
4. **Assembles responses** from multiple agents

```
Multi-Agent Architecture:
                    ┌─────────────────┐
                    │   SUPERVISOR    │
                    │   (Orchestrator)│
                    │                 │
                    │  - Intent route │
                    │  - NO tools     │
                    │  - Coordinates  │
                    └────────┬────────┘
                             │
           ┌─────────────────┼─────────────────┐
           │                 │                 │
           ▼                 ▼                 ▼
    ┌──────────┐      ┌──────────┐      ┌──────────┐
    │ RESEARCH │      │   MATH   │      │  WRITER  │
    │  AGENT   │      │  AGENT   │      │  AGENT   │
    │          │      │          │      │          │
    │ 5 tools  │      │ 3 tools  │      │ 4 tools  │
    └──────────┘      └──────────┘      └──────────┘
```

### Key Principles

1. **Supervisor has NO tools**: Only orchestration logic—delegates all execution
2. **Specialists are focused**: 3-10 tools per agent, clear capability boundaries
3. **Context is expensive**: Token count explodes in multi-agent; scope aggressively
4. **Hierarchy wins**: Clear supervisor → worker structure beats flat collaboration

### Intent Classification and Routing

The supervisor's primary job is routing requests to the right specialist:

```
Intent Classification Approaches:

1. LLM-Based Routing (Flexible, 1 extra call)
   User Query → Supervisor LLM → Agent Selection

   Pros: Handles ambiguity, learns from context
   Cons: Adds latency, costs tokens

2. Fine-Tuned Classifier (Fast, Cheap)
   User Query → BERT/DistilBERT → Agent Selection

   Pros: <100ms, cheap
   Cons: Needs training data, rigid categories

3. Semantic Routing (Cutting-Edge)
   User Query → Embedding → Similarity Match → Agent Selection

   Pros: <100ms, no training needed
   Cons: Requires good agent descriptions
```

**Critical Insight**: Misrouted requests cascade through incorrect agents, compounding errors. Invest heavily in routing accuracy.

### Context Transfer Between Agents

When Agent A completes and hands off to Agent B, context must transfer efficiently:

```
Context Transfer Patterns:

1. Full Context (Token Explosion)
   Agent A → [All Messages + State] → Agent B

   Problem: 8000+ tokens transferred

2. Selective Context (Efficient)
   Agent A → [Summary + Key Facts] → Agent B

   Approach: Filter irrelevant data, compress history

3. Structured Handoff (Production)
   Agent A → {
     summary: "Research complete",
     findings: [...],
     next_action: "Write documentation"
   } → Agent B
```

**Google ADK Principles** (2024):

-   Separate storage from presentation
-   Explicit transformations between formats
-   Scope by default—agents see only relevant context

## Orchestration Patterns

### Pattern 1: Supervisor-Worker

**Use Case**: Clear hierarchy with single decision-maker.

```
         ┌─────────────┐
         │  SUPERVISOR │
         │             │
         │ Decides:    │
         │ - Which     │
         │   agent     │
         │ - When done │
         └──────┬──────┘
                │
    ┌───────────┼───────────┐
    │           │           │
    ▼           ▼           ▼
┌───────┐  ┌───────┐  ┌───────┐
│Worker │  │Worker │  │Worker │
│   A   │  │   B   │  │   C   │
└───────┘  └───────┘  └───────┘
```

**Flow**:

1. User request arrives at supervisor
2. Supervisor analyzes and selects worker
3. Worker executes, returns result to supervisor
4. Supervisor decides: done, or route to another worker
5. Supervisor assembles final response

**Pros**:

-   ✅ Clear accountability (supervisor owns outcome)
-   ✅ Simple debugging (follow supervisor decisions)
-   ✅ Easy to add workers without changing others

**Cons**:

-   ❌ Supervisor bottleneck (all decisions through one point)
-   ❌ Extra latency (supervisor call before each worker)

### Pattern 2: Hierarchical Teams

**Use Case**: Complex domains requiring sub-specialization.

```
              ┌─────────────┐
              │   TOP-LEVEL │
              │  SUPERVISOR │
              └──────┬──────┘
                     │
         ┌───────────┴───────────┐
         │                       │
         ▼                       ▼
   ┌───────────┐           ┌───────────┐
   │  RESEARCH │           │ EXECUTION │
   │   TEAM    │           │   TEAM    │
   │ Supervisor│           │ Supervisor│
   └─────┬─────┘           └─────┬─────┘
         │                       │
    ┌────┴────┐             ┌────┴────┐
    │         │             │         │
    ▼         ▼             ▼         ▼
┌──────┐ ┌──────┐      ┌──────┐ ┌──────┐
│Web   │ │Data  │      │Code  │ │Deploy│
│Search│ │Analyst│     │Writer│ │Agent │
└──────┘ └──────┘      └──────┘ └──────┘
```

**Use When**:

-   6+ specialized agents
-   Natural domain groupings
-   Different teams need different context

**Pros**:

-   ✅ Scales to many agents
-   ✅ Natural domain boundaries
-   ✅ Team-level context isolation

**Cons**:

-   ❌ Increased latency (multiple supervisor hops)
-   ❌ Complex coordination
-   ❌ Risk of over-engineering

### Pattern 3: Orchestrator-Worker with Dynamic Routing

**Use Case**: Production systems with adaptive behavior.

```
┌─────────────────────────────────────────────┐
│              ORCHESTRATOR                   │
│                                             │
│  1. Analyze request                         │
│  2. Plan execution (which agents, order)    │
│  3. Execute plan (sequential or parallel)   │
│  4. Handle failures (retry, fallback)       │
│  5. Assemble response                       │
└─────────────────────────────────────────────┘
                    │
    ┌───────────────┼───────────────┐
    │               │               │
    ▼               ▼               ▼
┌───────┐      ┌───────┐      ┌───────┐
│Agent A│      │Agent B│      │Agent C│
└───────┘      └───────┘      └───────┘
```

**Key Innovation**: Orchestrator generates execution plan, not just single routing decision:

```typescript
// Execution plan schema
const planSchema = z.object({
	steps: z.array(
		z.object({
			agent: z.enum(["research", "math", "writer"]),
			task: z.string(),
			dependencies: z.array(z.string()).optional(),
			parallel: z.boolean().optional(),
		})
	),
	fallbackAgent: z.string().optional(),
});
```

**Pros**:

-   ✅ Handles complex multi-step tasks
-   ✅ Supports parallel execution
-   ✅ Built-in failure handling

**Cons**:

-   ❌ Planning overhead (extra LLM call)
-   ❌ Plan may be suboptimal

## Specialized Agent Types

### Planner/Architect Agent

**Role**: Strategic planning, read-only analysis, architecture decisions.

```
Capabilities:
-   Read codebase, documents, data
-   Generate plans, architectures, strategies
-   NO execution permissions

Tools: search, read_file, analyze_code, generate_plan

Model: GPT-4/Claude Opus (reasoning strength)
```

**Why Separate**: Planning requires different skills than execution. Planners benefit from larger models; executors can use cheaper models.

### Executor/Worker Agent

**Role**: Task execution with scoped permissions.

```
Capabilities:
-   Execute specific actions
-   Limited to assigned domain
-   Reports results back to supervisor

Tools: Domain-specific (e.g., write_file, run_query, send_email)

Model: GPT-3.5/Claude Haiku (cost efficiency)
```

**Permission Pattern**:

```
Executor Permission Levels:
├── Level 1: Read-only (safest)
├── Level 2: Create new (no modify/delete)
├── Level 3: Modify existing (no delete)
└── Level 4: Full CRUD (requires approval)
```

### Critic/Reviewer Agent

**Role**: Quality control, validation, feedback.

```
Capabilities:
-   Review outputs from other agents
-   Provide structured feedback
-   Flag issues, suggest improvements

Tools: validate, compare, score

Model: Medium tier (GPT-4-mini/Claude Sonnet)
```

**Generator-Critic Pattern**:

```
Generator Agent → Output → Critic Agent → Feedback
                     ↑                        │
                     └────────────────────────┘
                           (Iterate)
```

### Debug/Error Correction Agent

**Role**: Diagnose and fix failures from other agents.

```
Capabilities:
-   Analyze error logs, stack traces
-   Identify root causes
-   Suggest/apply fixes

Tools: read_logs, analyze_error, apply_fix

Pattern: ReAct with reflection
```

**Reflexion Pattern**: Agent reviews its own failures and generates improved approach:

```
Step 1: Agent attempts task
Step 2: Task fails
Step 3: Debug agent analyzes failure
Step 4: Debug agent suggests fix
Step 5: Original agent retries with fix
```

### Research/Information Agent

**Role**: Gather information from external sources.

```
Capabilities:
-   Web search, document retrieval
-   Data aggregation, summarization
-   Parallel information gathering

Tools: search_web, search_docs, summarize

Pattern: Parallel execution with aggregation
```

## Framework Integration

### AI SDK v6 Multi-Agent

**Sequential Pattern**:

```typescript
import { ToolLoopAgent } from "ai";
import { openai } from "@ai-sdk/openai";

const researchAgent = new ToolLoopAgent({
	model: openai("gpt-4-turbo"),
	instructions: "Research topics thoroughly.",
	tools: { searchWeb, analyzeData },
});

const writeAgent = new ToolLoopAgent({
	model: openai("gpt-4-turbo"),
	instructions: "Write clear documentation.",
	tools: { formatMarkdown },
});

async function sequentialWorkflow(topic: string) {
	// Step 1: Research
	const research = await researchAgent.generate({
		prompt: `Research: ${topic}`,
	});

	// Step 2: Write (uses research output)
	const doc = await writeAgent.generate({
		prompt: `Write documentation based on: ${research.content}`,
	});

	return doc.content;
}
```

**Orchestrator-Worker Pattern**:

```typescript
import { generateObject, ToolLoopAgent } from "ai";

async function orchestratorWorkflow(request: string) {
	// Orchestrator: Generate execution plan
	const { object: plan } = await generateObject({
		model: openai("gpt-4-turbo"),
		schema: z.object({
			tasks: z.array(
				z.object({
					agentType: z.enum(["research", "math", "writer"]),
					task: z.string(),
				})
			),
		}),
		prompt: `Plan tasks for: ${request}`,
	});

	// Execute workers (parallel where possible)
	const results = await Promise.all(plan.tasks.map(({ agentType, task }) => agents[agentType].generate({ prompt: task })));

	// Assemble response
	return results.map((r) => r.content).join("\n");
}
```

**Context Sharing via experimental_context**:

```typescript
interface SharedContext {
	sessionId: string;
	database: Database;
	services: ServiceContainer;
}

const agent = new ToolLoopAgent({
	model: openai("gpt-4-turbo"),
	tools: {
		queryDatabase: tool({
			description: "Query database",
			parameters: z.object({ query: z.string() }),
			execute: async (input, { experimental_context }) => {
				const ctx = experimental_context as SharedContext;
				return ctx.database.query(input.query);
			},
		}),
	},
});

await agent.generate({
	prompt: "Get user data",
	experimental_context: { sessionId, database, services },
});
```

## When to Use Multi-Agent

### ✅ Use Multi-Agent When:

1. **4+ Distinct Capabilities**

    - Different tools, different expertise
    - Example: Research + Analysis + Writing + Code

2. **Specialist Expertise Required**

    - Domain knowledge benefits from focused prompts
    - Example: Legal analysis requires specialized agent

3. **Iterative Refinement Needed**

    - Generator-critic patterns
    - Example: Code generation with review loop

4. **Long-Running Tasks**
    - Multiple stages over minutes/hours
    - Example: Research report with multiple sources

### ❌ Don't Use Multi-Agent When:

1. **Simple Retrieval**

    - Single tool, straightforward task
    - Better: Single RAG agent

2. **Latency Critical (<5s)**

    - Multi-agent adds 3x latency
    - Better: Optimized single agent

3. **Cost Constrained**

    - Multi-agent costs 3x more tokens
    - Better: Single agent with focused tools

4. **1-3 Tools Only**
    - Overhead not justified
    - Better: Single agent

### Decision Matrix

| Situation                    | Recommendation             |
| ---------------------------- | -------------------------- |
| <4 tools, simple tasks       | Single agent               |
| 4-10 tools, distinct domains | Supervisor-worker          |
| 10+ tools, natural groupings | Hierarchical teams         |
| Complex multi-step workflows | Orchestrator with planning |
| Real-time (<2s) requirements | Single agent with caching  |

## Production Best Practices

### 1. Start Simple, Add Complexity

**Approach**: Single agent → Add specialists only when proven necessary.

```
Evolution Path:
Week 1: Single agent with all tools
Week 2: Identify bottlenecks (which tools fail together?)
Week 3: Extract first specialist agent
Week 4: Measure improvement before adding more
```

**Why**: Multi-agent is 3x cost/latency. Justify before deploying.

### 2. External State Store

**Critical**: Most frameworks are in-memory. Production requires persistence.

```
Production Infrastructure:
├── Redis: Session state, inter-agent communication
├── PostgreSQL: Checkpoints, long-term memory
├── Job Queue (BullMQ): Async agent execution
└── Vector Store: Shared knowledge base
```

### 3. Rate Limiting Per Agent

**Control costs** by limiting each agent's API calls:

```typescript
const agentLimits = {
	research: { rpm: 10, tpm: 50000 }, // Expensive
	writer: { rpm: 20, tpm: 30000 }, // Medium
	validator: { rpm: 50, tpm: 10000 }, // Cheap
};
```

### Common Pitfalls

#### ❌ Pitfall 1: Flat Agent Collaboration

Agents "discuss" without clear hierarchy—leads to infinite loops and consensus failures.

**Solution**: Always have supervisor with termination authority.

#### ❌ Pitfall 2: Full Context Transfer

Passing all messages between agents—token explosion.

**Solution**: Summarize, filter, use structured handoffs.

#### ❌ Pitfall 3: No Graceful Degradation

Multi-agent fails, entire system fails.

**Solution**: Fallback to single agent on coordination failure.

## Observability & Debugging

### Multi-Agent Tracing

```
Trace Structure:
├── trace_id: "abc-123"
├── supervisor_decision: "route_to_research"
├── agent_executions:
│   ├── research_agent:
│   │   ├── steps: 3
│   │   ├── tools_called: ["search_web", "summarize"]
│   │   └── tokens: 2500
│   └── writer_agent:
│       ├── steps: 2
│       ├── tools_called: ["format_markdown"]
│       └── tokens: 1500
├── total_tokens: 4000
└── total_latency: 8.2s
```

### Key Metrics

| Metric                 | Target        | Alert Threshold |
| ---------------------- | ------------- | --------------- |
| Routing accuracy       | >95%          | <90%            |
| End-to-end latency     | <10s          | >20s            |
| Token usage per task   | <5000         | >10000          |
| Agent handoff failures | <2%           | >5%             |
| Supervisor overhead    | <20% of total | >30%            |

### Debugging Multi-Agent Failures

1. **Check routing**: Did supervisor select correct agent?
2. **Check context**: Did agent receive necessary information?
3. **Check individual agent**: Would agent succeed in isolation?
4. **Check assembly**: Did response aggregation work correctly?

## Key Takeaways

1. **Supervisor has NO tools**—delegates all execution to specialists
2. **5 tools per agent > 50 tools per agent**—focus improves reliability
3. **3x cost/latency overhead**—justify multi-agent before deploying
4. **Routing accuracy is critical**—misroutes cascade through system
5. **Context is expensive**—summarize, filter, scope aggressively
6. **Start single, evolve to multi**—add complexity only when proven necessary

**Quick Implementation Checklist**:

-   [ ] Define clear agent roles (planner, executor, critic, etc.)
-   [ ] Implement supervisor with routing logic
-   [ ] Design context transfer protocol (structured handoffs)
-   [ ] Add graceful degradation (fallback to single agent)
-   [ ] Set up tracing across all agents
-   [ ] Configure rate limits per agent
-   [ ] Test routing accuracy before production
