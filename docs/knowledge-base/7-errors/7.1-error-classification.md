## Overview

Traditional software fails loudly with stack traces and error codes. AI agents fail silently—returning plausible-looking outputs that are subtly wrong, looping infinitely without progress, or cascading a single mistake through multi-step reasoning chains.

Effective error recovery requires classification first. You can't retry a planning failure, can't fallback from a hallucination, and can't skip a cascading error. Each error type demands a specific recovery strategy.

**Key Research Findings** (2024-2025):

-   **24% higher accuracy**: AgentDebug framework using structured error taxonomy vs. baseline debugging
-   **87% root cause detection**: Automated classification achieves near-human accuracy on error diagnosis
-   **73% cascading failures**: Single root causes trigger multiple downstream failures in multi-agent systems

**Date Verified**: 2026-01-03

## The Problem: Agent Errors Are Invisible

### The Classic Challenge

A customer support agent processes a refund request. The tool call succeeds (200 OK), the database updates, the response looks correct. But the agent referenced an outdated order—wrong customer, wrong amount. The error is invisible until a human complaint arrives days later.

**Problems**:

-   ❌ No explicit error signals—code completes successfully
-   ❌ Traditional monitoring (error rates, status codes) misses semantic failures
-   ❌ Cascading errors propagate through multi-step reasoning before symptoms appear
-   ❌ Same symptom (wrong output) has different root causes requiring different fixes

### Why This Matters

-   **Silent failures** compound: 60%+ of agent issues are semantic, not technical
-   **Wrong recovery** wastes resources: Retrying a planning error just repeats the mistake
-   **Debugging time** explodes: Without classification, engineers chase symptoms instead of causes
-   **User trust** erodes: Users see confident-sounding wrong answers

## Core Concept

### What is Error Classification?

Error classification assigns agent failures to categories that map directly to recovery strategies. It answers: "What type of failure is this?" before asking "How do we fix it?"

### The Five-Module Taxonomy (AgentDebug)

Research analyzing 500+ failed agent trajectories identified five fundamental failure modules:

```
┌─────────────────────────────────────────────────────────────┐
│                    AGENT ERROR TAXONOMY                     │
├─────────────┬─────────────┬─────────────┬─────────────┬─────┤
│   MEMORY    │  REFLECTION │   PLANNING  │   ACTION    │ SYS │
├─────────────┼─────────────┼─────────────┼─────────────┼─────┤
│ Context     │ Self-assess │ Task decomp │ Tool select │ Rate│
│ loss        │ failures    │ errors      │ errors      │limit│
│             │             │             │             │     │
│ State       │ No error    │ Hallucinated│ Invalid     │ API │
│ inconsist.  │ recognition │ subtasks    │ arguments   │ down│
│             │             │             │             │     │
│ Retrieval   │ No          │ Wrong       │ Wrong       │ OOM │
│ failures    │ adaptation  │ reasoning   │ parameters  │     │
└─────────────┴─────────────┴─────────────┴─────────────┴─────┘
        ↓             ↓             ↓             ↓         ↓
    RECOVERY:     RECOVERY:     RECOVERY:     RECOVERY:  RECOVERY:
    Re-fetch      Re-prompt     Re-plan       Re-execute  Retry/
    context       with trace    from start    with fixes  Fallback
```

### Key Principles

1. **Classify Before Recovery**: Different error types need different strategies. Retrying a planning error just repeats it.

2. **Look for Root Cause**: 73% of multi-agent failures are cascading—find the origin, not the symptom.

3. **Silent > Loud**: The most dangerous errors produce valid-looking outputs. Prioritize semantic validation over status codes.

## Implementation Patterns

### Pattern 1: Three-Source Error Model

**Use Case**: Tool-using agents where failures can originate from inputs, context, or the tools themselves.

Errors arise from three sources with distinct characteristics:

```
Input Errors          Context Errors         Tool Errors
     ↓                     ↓                     ↓
 Explicit             Implicit               Silent
 (error msg)          (incomplete info)      (wrong output)
     ↓                     ↓                     ↓
 Easy to detect       Requires reasoning     Requires validation
```

**Input Errors**: Wrong arguments passed to tools
-   Usually produce explicit error messages
-   Recovery: Re-parse, re-prompt, or validate input schema

**Context Errors**: Incomplete environmental information
-   Common in interactive tasks with partial observability
-   Recovery: Fetch additional context, ask clarifying questions

**Tool Errors**: Tool executes but produces wrong result
-   No error signal—output looks valid
-   Recovery: Cross-validate, use checker tools, human review

**When to Use**: Any agent with external tool calls

### Pattern 2: Multi-Agent System Taxonomy (MAST)

**Use Case**: Multi-agent architectures where failures span agent boundaries.

MAST identifies 14 failure modes across three categories:

**Specification & System Design**:
-   Weak interface contracts between agents
-   Ambiguous task specifications
-   Missing error handling paths

**Inter-Agent Misalignment**:
-   Agents ignoring peer communications
-   Conflicting goals or assumptions
-   Poor coordination protocols

**Task Verification & Termination**:
-   Agents never reaching termination
-   Incorrect success criteria
-   Missing completion verification

**Metrics**: 50% average task completion across 7 popular MAS frameworks

**When to Use**: Any system with multiple cooperating agents

### Pattern 3: Execution Stage Classification

**Use Case**: Single-agent systems needing simple, actionable categories.

Three-tier model based on where in execution the error occurs:

| Stage | Error Type | Signal | Recovery |
|-------|-----------|--------|----------|
| **Planning** | Wrong decomposition | Output doesn't match intent | Re-plan from scratch |
| **Execution** | Tool failures | Explicit errors, timeouts | Retry, fallback |
| **Response** | Hallucinations | Semantic incorrectness | Re-generate, validate |

**When to Use**: Simpler agents, debugging initial implementations

## When to Use This Pattern

### ✅ Use When:

1. **Building Production Agents**
    - Classification enables automated recovery routing
    - Metrics improve with structured error categories

2. **Debugging Multi-Step Failures**
    - Taxonomy guides investigation toward root cause
    - Prevents chasing symptoms through long reasoning chains

3. **Designing Recovery Systems**
    - Each error class maps to specific recovery strategy
    - Prevents applying wrong fix (retry vs. re-plan vs. escalate)

### ❌ Don't Use When:

1. **Simple Completion APIs**
    - Single-turn, no tools, no state
    - Traditional error handling suffices

2. **Prototype Phase**
    - Focus on core functionality first
    - Add classification when reliability matters

### Decision Matrix

| Your Situation | Recommended Approach |
|---------------|---------------------|
| Tool-using single agent | Three-Source Model |
| Multi-agent system | MAST Taxonomy |
| Debugging existing agent | Execution Stage Classification |
| Building from scratch | Start with Execution Stage, evolve to full taxonomy |

## Production Best Practices

### 1. Log Classification, Not Just Errors

**Why**: Debugging requires knowing error type, not just that an error occurred.

Structure logs to capture:
-   Error module (Memory/Reflection/Planning/Action/System)
-   Error source (Input/Context/Tool)
-   Execution stage when detected
-   Cascade chain if applicable

**Impact**: Reduces mean time to root cause by 60-80%

### 2. Build Error Type Detectors

Agent can classify its own errors by observing patterns:

| Pattern | Likely Classification |
|---------|----------------------|
| Same tool called 3+ times with same args | Infinite loop (Action) |
| Output references non-existent entity | Hallucination (Response) |
| Tool returns success but state unchanged | Silent failure (Tool) |
| Task incomplete after max steps | Planning failure |

**Impact**: Enables automated recovery routing

### 3. Common Pitfalls

#### ❌ Pitfall 1: Treating All Errors as Transient

Assuming every error can be fixed by retry. Planning errors and hallucinations don't improve with retry—they need different context or re-planning.

**Solution**: Classify first, then select recovery strategy based on error type.

#### ❌ Pitfall 2: Chasing Symptoms in Cascades

In multi-agent systems, 73% of failures cascade. The visible error (final agent fails) is rarely the root cause.

**Solution**: Trace back through agent chain to find originating error. The first deviation from expected behavior is usually the root cause.

#### ❌ Pitfall 3: Over-Trusting Tool Success

Tools can return 200 OK with semantically wrong data. Status codes don't validate correctness.

**Solution**: Implement semantic validation for tool outputs, especially for tools that return structured data.

## Key Takeaways

1. **Agent errors differ from software errors**—they're silent, semantic, and cascading
2. **Classify before recovering**—wrong recovery strategy wastes resources and compounds errors
3. **Use the Five-Module Taxonomy** for comprehensive coverage: Memory, Reflection, Planning, Action, System
4. **73% of multi-agent failures cascade**—always trace to root cause before fixing
5. **Tool success ≠ semantic correctness**—validate outputs, not just status codes

**Quick Implementation Checklist**:

-   [ ] Add error classification to logging schema
-   [ ] Implement detectors for common patterns (loops, hallucinations, silent failures)
-   [ ] Map each error class to recovery strategy
-   [ ] Trace cascading errors to root cause before applying fix
-   [ ] Validate tool outputs semantically, not just syntactically
