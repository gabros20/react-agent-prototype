## Overview

When a tool or API degrades, naive retry logic makes things worse. Multiple agents hammer the struggling service, creating retry storms that delay recovery for everyone. The degradation cascades through the system as dependent services time out waiting.

Resilience patterns—circuit breakers, bulkheads, and timeouts—contain failures to their origin. They fail fast when recovery is unlikely, protecting both the agent and the degraded service.

**Key Research Findings** (2024-2025):

-   **Retry storms**: Without circuit breakers, retry attempts can 10x load on degraded services
-   **Cascading prevention**: Circuit breakers reduce cascade propagation by 80%+
-   **Recovery acceleration**: Fail-fast patterns reduce mean time to recovery by 40%

**Date Verified**: 2026-01-03

## The Problem: Cascading Failures

### The Classic Challenge

A database becomes slow under load. Agent A's query times out after 30 seconds. Agent A retries. Meanwhile, Agents B, C, D also timeout and retry. The retry storm adds 4x load to the already-struggling database. Response times increase further. More agents timeout. The cascade spreads.

```
Normal State                    Cascade State
─────────────                   ─────────────
Agent A ─┐                      Agent A ─┬─ Retry
Agent B ─┼─▶ DB (healthy)       Agent B ─┼─ Retry  ──▶ DB (overwhelmed)
Agent C ─┤                      Agent C ─┼─ Retry
Agent D ─┘                      Agent D ─┴─ Retry
```

**Problems**:

-   ❌ Retries amplify load on degraded services
-   ❌ Timeouts propagate up the call stack
-   ❌ One slow service takes down entire agent system
-   ❌ Recovery delayed by continued retry pressure

### Why This Matters

-   **Availability**: Cascade turns partial outage into total outage
-   **Cost**: Retries burn tokens and API quota on doomed requests
-   **Recovery**: Service can't recover while being hammered with retries
-   **User Experience**: All users affected, not just those using degraded path

## Core Concept

### The Three Resilience Patterns

```
┌─────────────────────────────────────────────────────────────┐
│                    RESILIENCE PATTERNS                      │
├───────────────────┬─────────────────┬───────────────────────┤
│  CIRCUIT BREAKER  │    BULKHEAD     │       TIMEOUT         │
├───────────────────┼─────────────────┼───────────────────────┤
│ Stops requests to │ Isolates        │ Bounds wait time      │
│ failing service   │ failures to     │ for responses         │
│                   │ compartments    │                       │
│ "Don't call if    │ "Failure in A   │ "Give up after X      │
│ it's broken"      │ doesn't affect  │ seconds"              │
│                   │ B"              │                       │
└───────────────────┴─────────────────┴───────────────────────┘
         ↓                   ↓                   ↓
   Prevents retry      Prevents cascade    Prevents blocking
   storms              propagation         indefinitely
```

### How They Work Together

```
Request arrives
     ↓
┌─────────────────┐
│ Circuit Open?   │──YES──▶ Fail immediately (no retry)
└────────┬────────┘
         │ NO
         ▼
┌─────────────────┐
│ Bulkhead Full?  │──YES──▶ Queue or reject (protect other paths)
└────────┬────────┘
         │ NO
         ▼
┌─────────────────┐
│ Execute with    │──TIMEOUT──▶ Cancel, record failure
│ timeout         │
└────────┬────────┘
         │ SUCCESS
         ▼
   Return result
```

### Key Principles

1. **Fail Fast**: When failure is likely, reject immediately rather than wait
2. **Contain Blast Radius**: Isolate failures so they don't spread
3. **Protect Recovery**: Stop hitting degraded services so they can heal
4. **Gradual Restoration**: Test recovery with limited traffic before full restore

## Implementation Patterns

### Pattern 1: Circuit Breaker

**Use Case**: Prevent retry storms against degraded services.

**State Machine**:
```
     ┌──────────────────────────────────────┐
     │                                      │
     ▼                                      │
┌─────────┐  Failure threshold   ┌────────┐│
│ CLOSED  │─────exceeded────────▶│  OPEN  ││
│(normal) │                      │(reject)││
└────┬────┘                      └───┬────┘│
     │                               │     │
     │                          Cooldown   │
     │                          elapsed    │
     │                               │     │
     │                               ▼     │
     │                         ┌─────────┐ │
     │◀───────Success─────────│HALF-OPEN│ │
     │                         │ (test)  │ │
     │                         └────┬────┘ │
     │                              │      │
     │                          Failure    │
     └──────────────────────────────┼──────┘
                                    │
                                    ▼
                              Back to OPEN
```

**States**:
-   **CLOSED**: Normal operation, requests pass through
-   **OPEN**: All requests fail immediately, no calls to service
-   **HALF-OPEN**: Limited test requests to check if service recovered

**Configuration**:

| Parameter | Recommended | Rationale |
|-----------|-------------|-----------|
| Failure threshold | 5 consecutive OR 50% in 100 requests | Balance sensitivity vs. noise |
| Open duration | 30-60 seconds | Give service time to recover |
| Half-open test count | 1-3 requests | Minimal traffic to test recovery |
| Sliding window | 100 requests or 60 seconds | Recent failures matter most |

**Per-Tool Circuit Breakers**: Each tool gets its own circuit. Slow search API doesn't block fast database lookups.

```
Agent
  ├── Tool A ──▶ Circuit A (CLOSED)
  ├── Tool B ──▶ Circuit B (OPEN) ──▶ Fail fast
  └── Tool C ──▶ Circuit C (CLOSED)
```

**Pros**:
-   ✅ Prevents retry storms
-   ✅ Fails fast when recovery unlikely
-   ✅ Protects recovering services

**Cons**:
-   ❌ Adds complexity
-   ❌ Brief outages during state transitions
-   ❌ Requires tuning per service

**When to Use**: Any external service call (APIs, databases, LLM providers)

### Pattern 2: Bulkhead

**Use Case**: Isolate failures to prevent cascade across system.

Named after ship bulkheads that contain flooding to one compartment. In agents, bulkheads limit concurrent requests to each dependency.

**Types**:

**Thread Pool Bulkhead**:
```
┌─────────────────────────────────────────┐
│                 Agent                    │
├──────────┬──────────┬───────────────────┤
│ Pool A   │ Pool B   │ Pool C            │
│ (5 max)  │ (10 max) │ (3 max)           │
│ Search   │ Database │ LLM               │
│ API      │          │                   │
└──────────┴──────────┴───────────────────┘

If Pool A exhausted → only Search blocked
Pools B, C continue normally
```

**Semaphore Bulkhead**:
-   Limits concurrent calls without dedicated threads
-   Lighter weight, suitable for async environments
-   Common in Node.js/TypeScript agents

**Configuration**:

| Dependency | Max Concurrent | Rationale |
|------------|---------------|-----------|
| Fast APIs (<100ms) | 20-50 | High throughput capacity |
| Slow APIs (1-5s) | 5-10 | Prevent thread starvation |
| LLM calls | 3-10 | Rate limits, cost control |
| Database | 10-20 | Connection pool alignment |

**Pros**:
-   ✅ Contains blast radius
-   ✅ Predictable resource usage
-   ✅ Other paths remain available

**Cons**:
-   ❌ Rejected requests need handling
-   ❌ Requires capacity planning
-   ❌ Under-provisioning wastes capacity

**When to Use**: Multi-tool agents, shared infrastructure, varying latency services

### Pattern 3: Timeout

**Use Case**: Prevent indefinite blocking on slow or hung services.

**Timeout Layers**:
```
┌─────────────────────────────────────────────────┐
│ Request Timeout (overall)         e.g., 30s    │
│  ┌──────────────────────────────────────────┐  │
│  │ Connection Timeout              e.g., 5s │  │
│  │  ┌────────────────────────────────────┐  │  │
│  │  │ Read Timeout (per response) e.g., 10s│ │  │
│  │  └────────────────────────────────────┘  │  │
│  └──────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**Configuration**:

| Timeout Type | Typical Value | Purpose |
|-------------|---------------|---------|
| Connection | 3-5s | Detect unreachable service fast |
| Read/Response | 10-30s | Bound wait for slow responses |
| Overall request | 30-60s | Cap total time including retries |
| Agent step | 60-120s | Prevent infinite tool loops |

**Timeout vs. Retry Interaction**:
```
Total budget: 60s
Per-attempt timeout: 15s
Max attempts: 3

Attempt 1: 0-15s (timeout)
Wait: 1s (backoff)
Attempt 2: 16-31s (timeout)
Wait: 2s (backoff)
Attempt 3: 33-48s (timeout)

Total: 48s, within 60s budget
```

**Pros**:
-   ✅ Predictable latency bounds
-   ✅ Prevents resource leaks
-   ✅ Simple to implement

**Cons**:
-   ❌ May cut off slow but successful operations
-   ❌ Requires service-specific tuning
-   ❌ Too short → false failures, too long → user frustration

**When to Use**: Every external call should have a timeout

## When to Use This Pattern

### ✅ Use When:

1. **Calling External Services**
    - LLM providers, APIs, databases—all can degrade
    - Without protection, one degraded service cascades

2. **Multi-Tool Agents**
    - Slow tool shouldn't block fast tools
    - Per-tool circuits prevent cross-contamination

3. **High-Traffic Systems**
    - Retry storms are more dangerous at scale
    - Circuit breakers essential above ~100 req/s

### ❌ Don't Use When:

1. **Single-User Prototypes**
    - No risk of retry storms
    - Simpler retry logic sufficient

2. **Offline/Batch Processing**
    - No real-time pressure
    - Can retry indefinitely

### Decision Matrix

| Situation | Circuit Breaker | Bulkhead | Timeout |
|-----------|-----------------|----------|---------|
| External API calls | ✅ Required | Optional | ✅ Required |
| Internal services | Optional | ✅ Recommended | ✅ Required |
| LLM providers | ✅ Required | ✅ Recommended | ✅ Required |
| Database queries | ✅ Recommended | ✅ Required | ✅ Required |
| File operations | Not needed | Not needed | ✅ Recommended |

## Production Best Practices

### 1. Start with Timeouts

Every external call needs a timeout. This is the minimum viable resilience. Add circuit breakers and bulkheads as you scale.

**Why**: Timeouts are simple, low-risk, and prevent the worst failures (indefinite hangs).

**Impact**: Predictable latency, bounded resource consumption

### 2. Tune Circuit Breaker Thresholds Per Service

Don't use the same thresholds everywhere. A flaky search API (10% error rate normal) needs different thresholds than a reliable database (0.1% error rate normal).

**Approach**:
-   Monitor baseline error rates for each service
-   Set threshold at 3-5x baseline error rate
-   Adjust based on production behavior

**Impact**: Fewer false opens, faster real failure detection

### 3. Monitor Circuit State Changes

Circuit breaker state changes are high-signal events. Track:
-   When circuits open (which service, why)
-   How long circuits stay open
-   Success rate of half-open tests
-   False open rate (circuit opened but service was healthy)

**Impact**: Identifies flaky services, validates thresholds

### 4. Common Pitfalls

#### ❌ Pitfall 1: Same Timeout for All Services

A 30-second timeout for a 50ms lookup wastes user time. A 5-second timeout for an LLM call that normally takes 10s causes false failures.

**Solution**: Profile each service's normal latency. Set timeout at p99 + buffer (e.g., p99 * 1.5).

#### ❌ Pitfall 2: Circuit Breaker Without Fallback

Circuit opens, all requests fail immediately. Users see errors instead of degraded service.

**Solution**: When circuit opens, fallback to cached data, cheaper model, or graceful degradation. Circuit breaker buys time for fallback logic.

#### ❌ Pitfall 3: Global Circuit Breaker for Multi-Instance Service

One bad instance opens circuit for entire service, even though other instances are healthy.

**Solution**: Per-instance circuit breakers when possible. Or use load balancer health checks to route around bad instances.

## Observability & Debugging

### Logging Strategy

**What to Log**:
-   Circuit state changes (CLOSED → OPEN, OPEN → HALF_OPEN, etc.)
-   Failure counts and types triggering state changes
-   Request rejection reasons (circuit open, bulkhead full, timeout)
-   Recovery success/failure in half-open state

**Why**: Circuit breaker decisions are critical for debugging production issues.

### Monitoring Metrics

| Metric | Target | Alert Threshold |
|--------|--------|-----------------|
| Circuit open rate | <1% | >5% |
| Bulkhead rejection rate | <0.1% | >1% |
| Timeout rate | <5% | >15% |
| False open rate | <10% of opens | >25% |

### Common Failure Modes

1. **Thrashing**: Circuit rapidly opens/closes
    - **Cause**: Threshold too sensitive, intermittent failures
    - **Fix**: Increase threshold, extend open duration

2. **Stuck Open**: Circuit never returns to closed
    - **Cause**: Half-open tests always fail, service degraded but not down
    - **Fix**: Check half-open test logic, verify service health

3. **Cascade Despite Circuits**: Failures still propagate
    - **Cause**: Timeouts too long, circuits share state incorrectly
    - **Fix**: Shorten timeouts, verify per-service circuit isolation

## Key Takeaways

1. **Timeout everything**—no external call should wait indefinitely
2. **Circuit breakers prevent retry storms**—fail fast when service is degraded
3. **Bulkheads contain blast radius**—slow service doesn't take down the system
4. **Per-service configuration**—one size doesn't fit all
5. **Monitor state changes**—circuit opens are high-signal events

**Quick Implementation Checklist**:

-   [ ] Add timeouts to every external call
-   [ ] Implement per-tool circuit breakers for critical dependencies
-   [ ] Configure bulkheads for varying-latency services
-   [ ] Set thresholds based on baseline service behavior
-   [ ] Monitor circuit state changes
-   [ ] Define fallback behavior when circuit opens
