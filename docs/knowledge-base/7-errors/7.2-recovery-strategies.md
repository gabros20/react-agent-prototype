## Overview

When an agent fails, the instinct is to retry. But retrying a planning error just repeats the mistake. Falling back to a cheaper model when the issue is bad input wastes resources. Escalating every error overwhelms human operators.

Effective recovery requires matching the strategy to the error type. This document provides a decision framework for selecting between four core strategies: retry, fallback, skip, and escalate.

**Key Research Findings** (2024-2025):

-   **90% reduction in failures**: Proper retry logic with exponential backoff for transient errors
-   **40% reduction in dead-ends**: Strategy selection based on error classification (SuperAGI)
-   **3x faster MTTR**: AI-driven diagnostics with correct recovery routing

**Date Verified**: 2026-01-03

## The Problem: One Size Doesn't Fit All

### The Classic Challenge

An agent encounters a tool error. The naive approach: retry 3 times with exponential backoff. But what if the tool is permanently down? The agent wastes time and tokens on doomed retries. What if the error is a hallucinated tool name? Retrying calls a non-existent endpoint forever.

**Problems**:

-   ❌ Retry storms when services are down—making recovery harder for everyone
-   ❌ Wasted compute and tokens on retries that can't succeed
-   ❌ Human escalation fatigue when every error triggers alerts
-   ❌ Silent failures when errors are skipped that should have escalated

### Why This Matters

-   **Cost**: Each LLM call costs money. Wrong recovery multiplies costs.
-   **Latency**: Users wait while agents retry doomed operations.
-   **Reliability**: Cascading failures when wrong strategy compounds errors.
-   **Trust**: Human operators stop responding to escalations if most are false alarms.

## Core Concept

### The Four Recovery Strategies

```
                     ┌─────────────────┐
                     │  Error Occurs   │
                     └────────┬────────┘
                              │
                     ┌────────▼────────┐
                     │   Classify      │
                     │   Error Type    │
                     └────────┬────────┘
                              │
        ┌─────────────┬───────┴───────┬─────────────┐
        │             │               │             │
        ▼             ▼               ▼             ▼
   ┌─────────┐  ┌──────────┐  ┌──────────┐  ┌───────────┐
   │  RETRY  │  │ FALLBACK │  │   SKIP   │  │ ESCALATE  │
   │         │  │          │  │          │  │           │
   │Transient│  │Persistent│  │Non-crit. │  │Unrecover. │
   │failures │  │failures  │  │steps     │  │or novel   │
   └─────────┘  └──────────┘  └──────────┘  └───────────┘
```

### Strategy Decision Tree

```
Is error transient?
├── YES: Can retry succeed?
│   ├── YES → RETRY with backoff
│   └── NO → Is there an alternative?
│       ├── YES → FALLBACK
│       └── NO → Is step critical?
│           ├── YES → ESCALATE
│           └── NO → SKIP
└── NO (persistent): Is there an alternative?
    ├── YES → FALLBACK
    └── NO → Is step critical?
        ├── YES → ESCALATE
        └── NO → SKIP
```

### Key Principles

1. **Classify First**: Never apply recovery without knowing error type
2. **Fail Fast**: Don't waste resources on doomed operations
3. **Preserve Progress**: Skip or compensate rather than restart entire task
4. **Escalate Sparingly**: Reserve human escalation for truly novel or high-stakes failures

## Implementation Patterns

### Pattern 1: Retry with Exponential Backoff

**Use Case**: Transient failures—network blips, rate limits, temporary service unavailability.

**How It Works**:
```
Attempt 1: Immediate
Attempt 2: Wait 1s + jitter
Attempt 3: Wait 2s + jitter
Attempt 4: Wait 4s + jitter
(cap at max delay, e.g., 60s)
```

**Why Jitter?** Without randomization, multiple agents waiting on the same backoff create a "thundering herd"—all retry simultaneously, overwhelming the recovering service.

**Configuration**:

| Parameter | Recommended | Rationale |
|-----------|-------------|-----------|
| Initial delay | 250-750ms | Fast recovery for brief blips |
| Backoff factor | 1.5-2x | Exponential growth without excessive waits |
| Max delay | 30-60s | Cap to prevent indefinite waits |
| Max attempts | 3-5 | Diminishing returns after ~5 retries |
| Jitter | Full random | Distribute load across time window |

**Retry Budget**: Track cumulative retry time. If total exceeds budget (e.g., 2 minutes), stop retrying and escalate.

**When to Use**: Rate limits (429), timeouts, connection errors, 5xx server errors

**When NOT to Use**: 4xx client errors (bad request won't improve), authentication failures, validation errors

### Pattern 2: Fallback to Alternative

**Use Case**: Primary path unavailable but alternatives exist.

**Fallback Hierarchy**:
```
Primary Tool/Model
     ↓ (failure)
Secondary Tool/Model
     ↓ (failure)
Cached/Stale Data
     ↓ (failure)
Degraded Functionality
     ↓ (failure)
Human Escalation
```

**Common Fallback Patterns**:

| Primary | Fallback | Trade-off |
|---------|----------|-----------|
| GPT-4 | GPT-3.5 | Quality for availability |
| Live API | Cached data | Freshness for reliability |
| Full analysis | Summary | Depth for speed |
| Automated decision | Human review | Speed for accuracy |

**Provider Rotation**: When one LLM provider rate-limits, route to another. Requires multi-provider setup but dramatically improves availability.

**When to Use**: Provider outages, quota exhaustion, consistent timeouts on primary

**When NOT to Use**: Errors caused by bad input (fallback will fail the same way)

### Pattern 3: Skip with Compensation

**Use Case**: Non-critical steps that can be deferred or omitted.

**Skip Criteria**:
-   Step is optional (nice-to-have, not must-have)
-   Downstream steps don't depend on this result
-   Compensating action can restore consistency later

**Saga Pattern for Reversible Operations**:
```
Action: Debit account $100
→ Result: Success
→ Next Action: Check inventory
→ Result: Inventory insufficient
→ Compensation: Credit account $100 (restore state)
```

Each action has a defined compensating action. On failure, execute compensations in reverse order.

**When to Use**:
-   Enrichment steps (adding optional metadata)
-   Logging/analytics that don't affect core functionality
-   Parallelizable steps where some can fail

**When NOT to Use**:
-   Steps that affect data integrity
-   Operations without compensating actions
-   Sequential dependencies

### Pattern 4: Escalate to Human

**Use Case**: Unrecoverable failures, novel errors, high-stakes decisions.

**Escalation Triggers**:
-   All automated recovery strategies exhausted
-   Error type not recognized (novel failure)
-   Decision has compliance/legal implications
-   User explicitly requested human review
-   Confidence below threshold on critical operation

**Escalation Quality**:

Good escalation includes:
-   What the agent was trying to do
-   What failed and why
-   What recovery strategies were attempted
-   Recommended action with confidence
-   All relevant context for human decision

Bad escalation: "An error occurred. Please review."

**Preventing Alert Fatigue**:
-   Batch non-urgent escalations
-   Route to appropriate specialist (not generic queue)
-   Include severity/priority classification
-   Track escalation patterns to identify automation opportunities

**When to Use**:
-   Compliance-sensitive operations
-   Customer-facing decisions with reputational risk
-   Budget/resource decisions above threshold
-   Novel errors not seen in training data

## When to Use This Pattern

### ✅ Use When:

1. **Building Production Agents**
    - Different errors need different responses
    - Framework prevents wasted resources on wrong recovery

2. **Multi-Step Agent Tasks**
    - Some steps can be skipped, others must succeed
    - Compensation enables partial rollback

3. **Multi-Provider Architectures**
    - Fallback between providers increases availability
    - Retry storms affect all customers, not just you

### ❌ Don't Use When:

1. **Single-Turn Completions**
    - Simple retry is sufficient
    - No complex recovery needed

2. **Development/Testing**
    - Fail fast to surface issues
    - Complex recovery masks bugs

### Decision Matrix

| Error Type | First Strategy | Second Strategy | Last Resort |
|------------|---------------|-----------------|-------------|
| Rate limit (429) | Retry with backoff | Fallback provider | Escalate |
| Timeout | Retry (1-2x) | Fallback | Skip or escalate |
| Bad request (400) | Fix input | Escalate | — |
| Auth failure (401/403) | Refresh token | Escalate | — |
| Not found (404) | Create resource | Skip | Escalate |
| Server error (5xx) | Retry with backoff | Fallback | Escalate |
| Hallucination | Re-prompt with correction | Fallback model | Escalate |
| Planning error | Re-plan from scratch | Escalate | — |

## Production Best Practices

### 1. Implement Recovery Budgets

**Why**: Unbounded recovery wastes resources and delays failure notification.

Set budgets for:
-   **Time budget**: Max total time for all recovery attempts (e.g., 2 minutes)
-   **Retry budget**: Max number of retries per error (e.g., 5)
-   **Cost budget**: Max additional tokens/API calls for recovery
-   **Cascade budget**: Max depth of fallback chain (e.g., 3 levels)

**Impact**: Predictable failure timing, bounded resource consumption

### 2. Log Recovery Attempts

Track for each recovery:
-   Strategy selected and why
-   Outcome (success/failure)
-   Time and resources consumed
-   Final resolution (recovered/escalated/failed)

**Why**: Identifies patterns for automation and reveals ineffective strategies.

**Impact**: Continuous improvement of recovery logic

### 3. Common Pitfalls

#### ❌ Pitfall 1: Retry Everything

Retrying non-transient errors wastes resources and delays proper recovery.

**Solution**: Check error type before retrying. Only retry transient failures (rate limits, timeouts, 5xx errors). Immediately fallback or escalate for client errors, auth failures, validation errors.

#### ❌ Pitfall 2: Fallback to Same Failure Mode

Falling back to a cheaper model when the issue is bad input—the fallback fails identically.

**Solution**: Fallback only changes the execution path, not the input. If input is wrong, fix input first. Only fallback when the issue is with the executor, not the request.

#### ❌ Pitfall 3: Silent Skip of Critical Steps

Skipping a step that downstream logic depends on causes cascading failures.

**Solution**: Before skipping, verify no downstream dependencies. If dependencies exist, either satisfy with default/cached value or escalate rather than skip.

#### ❌ Pitfall 4: Escalation Without Context

"An error occurred" tells humans nothing. They waste time reconstructing context.

**Solution**: Include: what was attempted, what failed, what was tried, recommended action. Give humans enough context to decide in <30 seconds.

## Key Takeaways

1. **Match strategy to error type**—retry for transient, fallback for persistent, skip for optional, escalate for novel
2. **Implement budgets**—bound time, retries, and cost to prevent runaway recovery
3. **Add jitter to retries**—prevent thundering herd on recovering services
4. **Fallback changes executor, not input**—don't fallback when the request itself is wrong
5. **Escalate with context**—include what/why/tried/recommended for fast human decisions

**Quick Implementation Checklist**:

-   [ ] Classify errors before selecting recovery strategy
-   [ ] Implement exponential backoff with jitter for retries
-   [ ] Define fallback hierarchy for critical tools
-   [ ] Set budgets for time, retries, and cost
-   [ ] Include full context in escalations
-   [ ] Log all recovery attempts for analysis
