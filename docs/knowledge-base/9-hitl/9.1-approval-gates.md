# 9.1 Approval Gates & Confirmation

## TL;DR

Approval gates pause agent execution before high-risk actions, requiring explicit human confirmation—use `needsApproval` in AI SDK v6 or `interrupt()` in LangGraph to enforce checkpoints for destructive operations, payments, and data modifications.

## Overview

Human-in-the-loop (HITL) approval gates intentionally pause autonomous agent workflows at critical decision points. Instead of letting an agent execute tasks end-to-end, approval gates add user confirmation checkpoints before destructive, expensive, or sensitive actions proceed.

This isn't a temporary workaround—it's a **long-term pattern for building AI agents we can trust**, ensuring LLMs stay within safe operational boundaries and teams remain in control even as autonomy grows.

**Key Research Findings** (2024-2025):

-   **69% of enterprises** deploy AI agents, but only 21% have adequate security visibility (Obsidian Security, 2025)
-   **EU AI Act Article 14** requires high-risk AI systems to support human intervention, override, and audit logging
-   **Progressive trust model** recommended: start with more oversight, gradually relax as confidence builds
-   **Risk-tiered actions** reduce approval fatigue while maintaining safety for critical operations

**Date Verified**: 2026-01-04

## The Problem: Autonomous Agents Without Guardrails

### The Classic Challenge

An agent with database write access receives a request to "clean up old user data." Without approval gates, it might delete production records before anyone reviews the scope, query, or consequences.

```
User: "Delete all inactive users from the database"

Agent (without gates):
  1. Queries database for inactive users
  2. Finds 50,000 records
  3. Executes DELETE statement
  4. Returns "Done! Deleted 50,000 users" ← Irreversible

Agent (with gates):
  1. Queries database for inactive users
  2. Finds 50,000 records
  3. PAUSES → "About to delete 50,000 users. Proceed?"
  4. Human reviews, modifies criteria if needed
  5. Approves or rejects
```

**Problems**:

-   ❌ **Irreversible actions**: Deletions, payments, deployments can't be undone
-   ❌ **Scope creep**: Agent interprets request more broadly than intended
-   ❌ **Silent failures**: Wrong tool selection executes without validation
-   ❌ **Compliance violations**: Regulated industries require human oversight

### Why This Matters

-   **Trust**: Users need confidence that agents won't take unexpected actions
-   **Compliance**: Regulations (GDPR, HIPAA, PCI-DSS) mandate human oversight
-   **Safety**: High-risk domains (healthcare, finance) require validation
-   **Debugging**: Approval points create natural checkpoints for understanding agent behavior

## Core Concept

### What Are Approval Gates?

Approval gates are explicit checkpoints where agent execution pauses, presents the proposed action to a human, and waits for a decision before proceeding.

```
Agent Execution Flow
        │
        ▼
┌───────────────────┐
│   Plan Action     │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Is High-Risk?     │
└─────────┬─────────┘
          │
    ┌─────┴─────┐
    │           │
    ▼           ▼
   No          Yes
    │           │
    ▼           ▼
┌────────┐  ┌────────────────┐
│Execute │  │ PAUSE          │
│        │  │ Present to     │
│        │  │ Human          │
└────────┘  └───────┬────────┘
                    │
              ┌─────┴─────┐
              │           │
              ▼           ▼
           Approve      Reject
              │           │
              ▼           ▼
         ┌────────┐  ┌────────┐
         │Execute │  │ Cancel │
         │        │  │ or     │
         │        │  │ Modify │
         └────────┘  └────────┘
```

### Risk-Tiering Framework

Not every action needs approval. Classify tools by risk level:

| Tier | Risk Level | Approval | Examples |
|------|------------|----------|----------|
| **Autonomous** | Low | Auto-approve | Read operations, queries, `ls` |
| **Approval Required** | Medium-High | Human confirms | Data writes, API calls, uploads |
| **Prohibited** | Critical | Multi-approval or blocked | Prod deletions, payment processing |

### Key Principles

1. **Explicit Checkpoints**: Identify where human input is critical—access approvals, configuration changes, destructive actions
2. **Clear Context**: Present what the action will do, not just raw parameters
3. **Progressive Trust**: Start conservative, expand autonomy based on track record
4. **Audit Trail**: Log all approvals, rejections, and reasoning

## Implementation Patterns

### Pattern 1: Static Approval (Always Require)

**Use Case**: Destructive operations that always need confirmation regardless of context.

```typescript
const deleteDatabase = tool({
  description: "Permanently delete a database",
  parameters: z.object({
    databaseId: z.string().uuid(),
  }),
  needsApproval: true, // Always requires approval
  execute: async ({ databaseId }, { experimental_context }) => {
    const ctx = experimental_context as AgentContext;
    await ctx.services.database.delete(databaseId);
    return { success: true, deleted: databaseId };
  },
});
```

**Pros**:
-   ✅ Simple, explicit
-   ✅ No edge cases to consider
-   ✅ Clear audit trail

**Cons**:
-   ❌ May cause approval fatigue for frequent operations

**When to Use**: File deletions, payment processing, production deployments

### Pattern 2: Dynamic Approval (Conditional)

**Use Case**: Approval based on input parameters, context, or thresholds.

```typescript
const sendEmail = tool({
  description: "Send an email to a recipient",
  parameters: z.object({
    to: z.string().email(),
    subject: z.string(),
    body: z.string(),
  }),
  // Approve based on content
  needsApproval: async (_ctx, { to, subject }) => {
    const isExternalDomain = !to.endsWith("@company.com");
    const isSensitiveTopic = /confidential|salary|termination/i.test(subject);
    return isExternalDomain || isSensitiveTopic;
  },
  execute: async ({ to, subject, body }) => {
    await emailService.send({ to, subject, body });
    return { success: true, sent: true };
  },
});
```

**Pros**:
-   ✅ Reduces approval fatigue for safe operations
-   ✅ Context-aware decisions
-   ✅ Can incorporate user preferences

**Cons**:
-   ❌ Logic complexity increases
-   ❌ Must maintain approval rules

**When to Use**: Operations where risk varies by input (amount thresholds, external vs internal)

### Pattern 3: Approval Queue (Enterprise Scale)

**Use Case**: Multiple concurrent approval requests with SLAs and routing.

```
┌─────────────────────────────────────────────────────────────┐
│                    APPROVAL QUEUE                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Request    Priority   Type        Reviewer    SLA         │
│  ─────────────────────────────────────────────────────      │
│  #1234      HIGH       Payment     Finance     15 min      │
│  #1235      MEDIUM     Delete      Manager     1 hour      │
│  #1236      LOW        Export      Data Team   4 hours     │
│                                                             │
│  Workflow:                                                  │
│  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐    │
│  │ Triage  │──▶│ Review  │──▶│ Approve │──▶│ Execute │    │
│  │         │   │         │   │ /Reject │   │         │    │
│  └─────────┘   └─────────┘   └─────────┘   └─────────┘    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Queue Components**:
-   **Triage Reviewer**: Quick approve/reject/escalate decisions
-   **Priority Routing**: Customer impact, safety, deadlines
-   **SLA Tracking**: Time-to-first-review, time-to-resolution
-   **Auto-Resolution**: Low-risk items resolved with validators

**When to Use**: High-volume environments with multiple approvers and compliance requirements

### Pattern 4: Two-Phase Commit

**Use Case**: Critical operations requiring staged execution with rollback capability.

```
Phase 1: STAGE
    │
    ▼
┌───────────────────┐
│ Stage Changes     │
│ (Reversible)      │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Validate          │
│ Invariants        │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ PAUSE for         │
│ Human Approval    │
└─────────┬─────────┘
          │
    ┌─────┴─────┐
    │           │
    ▼           ▼
Phase 2:      Rollback
COMMIT
```

**When to Use**: Database migrations, financial transactions, multi-step workflows

## Framework Integration

### AI SDK v6 Implementation

AI SDK v6 provides native approval support via the `needsApproval` flag:

```typescript
// tools/payment.ts
import { tool } from "ai";
import { z } from "zod";

export const processPayment = tool({
  description: "Process a payment transaction",
  parameters: z.object({
    amount: z.number().positive(),
    currency: z.enum(["USD", "EUR", "GBP"]),
    recipientId: z.string().uuid(),
  }),
  needsApproval: true,
  execute: async ({ amount, currency, recipientId }, { experimental_context }) => {
    const ctx = experimental_context as AgentContext;
    const result = await ctx.services.payments.process({
      amount,
      currency,
      recipientId,
    });
    return { success: true, transactionId: result.id };
  },
});
```

**Frontend Integration (React)**:

```typescript
"use client";
import { useChat } from "@ai-sdk/react";
import { DefaultChatTransport, isStaticToolUIPart, getStaticToolName } from "ai";

export function ChatWithApproval() {
  const { messages, addToolOutput, sendMessage } = useChat({
    transport: new DefaultChatTransport({ api: "/api/chat" }),
  });

  const handleApproval = async (toolCallId: string, toolName: string, approved: boolean) => {
    await addToolOutput({
      toolCallId,
      tool: toolName,
      output: approved ? "APPROVED" : "DENIED",
    });
    sendMessage();
  };

  return (
    <div>
      {messages.map((m) => (
        <div key={m.id}>
          {m.parts?.map((part, i) => {
            if (isStaticToolUIPart(part) && part.state === "input-available") {
              const toolName = getStaticToolName(part);
              return (
                <div key={i} className="approval-modal">
                  <h3>Approval Required: {toolName}</h3>
                  <pre>{JSON.stringify(part.input, null, 2)}</pre>
                  <button onClick={() => handleApproval(part.toolCallId, toolName, true)}>
                    Approve
                  </button>
                  <button onClick={() => handleApproval(part.toolCallId, toolName, false)}>
                    Deny
                  </button>
                </div>
              );
            }
            return part.type === "text" ? <p key={i}>{part.text}</p> : null;
          })}
        </div>
      ))}
    </div>
  );
}
```

### LangGraph Implementation

LangGraph uses `interrupt()` for human checkpoints:

```python
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, interrupt
from langgraph.checkpoint.postgres import PostgresSaver
from typing import TypedDict, Literal

class WorkflowState(TypedDict):
    action: str
    params: dict
    approved: bool
    result: str

def request_approval(state) -> Command[Literal["execute", "cancel"]]:
    """Pause for human approval."""
    response = interrupt({
        "question": f"Approve {state['action']}?",
        "params": state["params"],
        "risk": "HIGH"
    })

    if response["action"] == "approve":
        return Command(
            update={"approved": True},
            goto="execute"
        )
    else:
        return Command(
            update={"approved": False},
            goto="cancel"
        )

def execute_action(state):
    result = perform_action(state["action"], state["params"])
    return {"result": result}

def cancel_action(state):
    return {"result": "Action cancelled by user"}

# Build graph
builder = StateGraph(WorkflowState)
builder.add_node("approve", request_approval)
builder.add_node("execute", execute_action)
builder.add_node("cancel", cancel_action)

builder.add_edge(START, "approve")
builder.add_edge("execute", END)
builder.add_edge("cancel", END)

graph = builder.compile(checkpointer=PostgresSaver(...))

# Execute - pauses at interrupt
config = {"configurable": {"thread_id": "workflow-123"}}
result = graph.invoke({"action": "delete_database", "params": {"id": "prod-1"}}, config)

# Resume after human decision
graph.invoke(Command(resume={"action": "approve"}), config)
```

**Key Behavior**: When `interrupt()` is called, LangGraph saves state and pauses indefinitely. The workflow can be resumed days later, even on a different server.

### Amazon Bedrock Patterns

Bedrock offers two approaches:

**User Confirmation**: Simple boolean approve/reject
```python
# Agent pauses, returns confirmation request
# User approves or rejects
# Agent continues or terminates
```

**Return of Control (ROC)**: Full parameter modification
```python
# Agent returns invocationInputs + invocationId
# Developer can modify parameters before execution
# Provides maximum flexibility for complex workflows
```

## When to Use This Pattern

### ✅ Use When:

1. **Destructive Operations**
    - Database deletions, file removals
    - Infrastructure teardown
    - Irreversible state changes

2. **Financial Operations**
    - Payment processing
    - Refunds above threshold
    - Budget modifications

3. **External Communications**
    - Emails to external parties
    - API calls to third-party services
    - Public-facing content publishing

4. **Compliance Requirements**
    - HIPAA (PHI access)
    - PCI-DSS (payment data)
    - GDPR (data deletion)

### ❌ Don't Use When:

1. **Read-Only Operations**
    - Data queries, searches
    - Status checks
    - Non-sensitive reads

2. **Idempotent Safe Operations**
    - Operations that can be safely retried
    - Internal logging, metrics

3. **High-Frequency Low-Risk**
    - Would cause approval fatigue
    - Better served by rate limits or budgets

### Decision Matrix

| Situation | Recommended Approach |
|-----------|---------------------|
| Production database write | Static approval (always) |
| Email to internal team | No approval needed |
| Email to external party | Dynamic approval |
| Payment < $10 | No approval |
| Payment > $100 | Static approval |
| File deletion | Static approval |
| Data export | Dynamic (based on sensitivity) |

## Production Best Practices

### 1. Clear, Actionable Requests

Present approvals with context, not raw data:

```
❌ Bad: "Approve tool call: deleteUser({id: 'abc123'})"

✅ Good: "Delete user John Doe (john@example.com)?
         - Account created: 2023-01-15
         - Last active: 2025-12-01
         - Associated data: 47 records
         This action is permanent."
```

**Impact**: Reduces approval errors, builds reviewer confidence

### 2. Timeout and Escalation

Don't let approvals block indefinitely:

```typescript
const approvalConfig = {
  timeout: 15 * 60 * 1000, // 15 minutes
  escalation: {
    after: 10 * 60 * 1000, // Escalate after 10 min
    to: "manager@company.com",
  },
  fallback: "reject", // Default action on timeout
};
```

**Impact**: Prevents workflow deadlocks, maintains SLAs

### 3. Common Pitfalls

#### ❌ Pitfall 1: Approval Fatigue

Too many low-risk approvals cause reviewers to approve without reading.

**Solution**: Risk-tier actions, auto-approve low-risk with validators, track reviewer engagement metrics.

#### ❌ Pitfall 2: Hardcoded Rules

Approval logic scattered across codebase, hard to audit.

**Solution**: Centralize in policy engine (Permit.io, OPA). Declarative rules are versionable and auditable.

#### ❌ Pitfall 3: Missing Audit Trail

No record of who approved what and when.

**Solution**: Log every approval decision with timestamp, user, action details, and reasoning.

### 4. Security Considerations

-   **Principle of Least Privilege**: Agents start with read-only, gain write access per-approval
-   **Dual Control**: Critical operations require two approvals
-   **Token Scoping**: Limit agent API access to necessary operations
-   **Behavioral Monitoring**: Detect anomalous approval patterns

## Key Takeaways

1. **Approval gates are essential for trust**—pause before destructive, expensive, or sensitive actions
2. **Risk-tier your actions**—not everything needs approval; focus on high-impact operations
3. **Use native framework support**—AI SDK `needsApproval`, LangGraph `interrupt()` are battle-tested
4. **Present clear context**—reviewers need to understand what they're approving
5. **Start conservative, expand gradually**—prove trustworthiness before reducing oversight

**Quick Implementation Checklist**:

-   [ ] Identify high-risk tools (deletions, payments, external calls)
-   [ ] Add `needsApproval: true` to critical tools
-   [ ] Build approval UI (modal, queue, or notification)
-   [ ] Implement timeout and escalation
-   [ ] Set up audit logging
-   [ ] Define risk tiers and approval routing
